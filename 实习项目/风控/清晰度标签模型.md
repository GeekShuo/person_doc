# ocr预标签
OCR预标签设计思路
为了节约人力成本，我首先使用OCR模型，通过其给出的置信度，结合一些图像特征，对当前的这些一万多条给出了一个预标签
初版规则如下：
https://doc.weixin.qq.com/smartpage/a1_AcIA0QY5AEkCNFyRKxHrgRzKetsiP?scode=AJEAIQdfAAoZTHGcmy 
该规则中有几个关键设计
1.OCR框的置信度低于80%，则认为该框内文字不可辨、不可用
2.整体阈值档位划分为10% 50% 90%。之所以允许优秀档位有10%的不可辨文字，因为发现实际图像经常由于印章的存在降低可辨率，少有只有某一个特定地方模糊的文书，所以10%以下的都归位优质文书
3.增加了漏检补偿机制，许多文书有些部分过于模糊，直接没有被ocr模型框出来，所以要根据图像特征判断有没有漏检，漏检的图像质量降级
预标签结果V1
规则给出的标注结果，经过人工复核后如下
https://doc.weixin.qq.com/smartsheet/s3_AcIA0QY5AEkCNZqijdwS7RcuvM7B1?scode=AJEAIQdfAAoYusSHXL 
其中，ocr规则判断562条问题文书，其中有262条文书经过人工复核认为不应定为模糊。对这部分文书逐条复核原因，得到如下结论
    1。 漏检补偿是大头，很多文书可能背景比较黑，或者线条多，这部分被错误判断为了文字像素。之前的Otsu方案Otsu二值化是纯图像处理方法，它把所有暗像素都当成"可能是文字"，然后用连通区域分析来估算漏检。问题是法律文书里有很多非文字的暗区域——黑边框、签名、印章、装饰线、表格线残影——Otsu分不清这些和真正的文字，导致清晰图片也被判定为"有大量漏检文字"。因此，替换为DBNet方案：对同一张图跑两次DBNet检测，一次用正常阈值(0.5)只检测清晰文字，一次用低阈值(0.15)检测包括模糊文字在内的所有文字区域。两次结果的差值就是"模糊到差点检测不到的文字"面积。因为DBNet是训练过的文字检测器，它不会把黑边、签名、装饰图案当成文字，所以不会误判。
    替换为DBNet处理后，结果如下：
    DBNet boost分布：0=289条（不补偿），+1=6条，+2=7条
        而旧的Otsu方法：302条里199条都在补偿（+1或+2），但其中绝大多数是误判——旧方法给出的漏检比例普遍在0.25-0.97，DBNet给出的几乎全是0.00-0.05。
    DBNet 能排除的：
    - 线框/表格线：DBNet天然不检测，因为线条没有文字的形态特征
    - 二维码：DBNet天然不检测，黑白方块不是文字模式
    - 黑色边框/暗背景：DBNet天然不检测
            
            DBNet 不能排除的：
    - 印章：DBNet会把印章里的弯曲文字当成文字检测出来，需要后置过滤

# OCR模型原理
paddle官方有两大模型体系，最新版分别为PP-OCRv6 与 PaddleOCR-VL 1.6
分别由以下小模型流水线处理组合而成
├── models/
│   ├── paddleocr_v6/              # PP-OCRv6 ONNX 版本
│   │   ├── det/inference.onnx
│   │   └── rec/inference.onnx
│   └── paddleocr_vl_1.6/          # PaddleOCR-VL 1.6 全套 Paddle 原生模型
│       ├── PaddleOCR-VL-1.6/          # 1.8G  VL 主模型
│       ├── PP-DocLayoutV2/            # 204M  版面检测
│       ├── PP-DocBlockLayout/         # 124M  精细化块检测（可选）
│       ├── PP-OCRv6_medium_det/       #  60M  文本行检测
│       ├── PP-OCRv6_medium_rec/       #  74M  文本行识别
│       ├── PP-FormulaNet_plus-L/      # 702M  公式识别
│       ├── SLANeXt_wired/             # 349M  有线表格
│       ├── SLANeXt_wireless/          # 349M  无线表格
│       ├── PP-Chart2Table/            # 1.4G  图表转表
│       ├── PP-LCNet_x1_0_doc_ori/     # 6.6M  文档方向分类
│       ├── PP-LCNet_x0_25_textline_ori/ # 1.1M  行方向分类
│       └── UVDoc/                     #  31M  文档矫正
PP-OCRv6（两阶段）
输入图 ──▶ [det: PP-OCRv6_medium_det] ──▶ 文本框 polygons
                                              │
                                              ▼
                         切块 ──▶ [rec: PP-OCRv6_medium_rec] ──▶ (text, score)
- det：LCNetV4 backbone + RepLKFPN neck + DB 后处理，输出多边形框
- rec：LCNetV4 backbone + SVTR encoder（局部+全局注意力），CTC 解码，输出字符串
- 参数量：det 15.5M + rec 18.9M，合计约 34.5M
- 不做版面理解，纯字符输出
经过测试，在纯结构化的文档OCR识别任务场景下，OCRV6的准确率、响应速度、显存占用，都要优于VL
可以把整个 OCR 拆成两个问题：

① 这里是不是文字？ → Dec 检测
② 如果是文字，它具体写的是什么？ → Recognition 识别
det阶段处理流程
1. LCNetV4 Backbone：负责“看图、提特征”
这一部分还不知道哪里是文字框。
例如输入：
┌─────────────────────────────┐
│                             │
│       Hello World           │
│                             │
│     🏠     🚗     🌳        │
└─────────────────────────────┘
Backbone 做的事情类似 CNN/ViT 的特征提取：
Input
 ↓
Conv / Block
 ↓
Feature Map
 ↓
Feature Map
 ↓
Feature Map
最终得到不同尺度的 feature：
F1：高分辨率，细节多
F2：中分辨率
F3：低分辨率，语义强
F4：更低分辨率
它学习的不是“这里有一个文字框”，而是“这个区域有什么视觉特征？”
例如文字的横竖笔画、边缘、字符结构、局部纹理、长宽比例、字符排列、背景特征等信息，Backbone 更像是视觉特征提取器。
2. RepLKFPN：负责“把不同尺度的信息合起来”
这个非常重要。
因为文字的尺度差异特别大，如果只使用最后一层低分辨率（大感受野） 小文字可能丢失细节。如果只使用浅层细节丰富，但是缺乏高级语义
所以 FPN 做：
Backbone

F1 ───────────────┐
                  ↓
F2 ────────────→ FPN
                  ↓
F3 ────────────→ 融合
                  ↓
F4 ──────────────┘
        ↓

Multi-scale Feature
RepLKFPN 的特点之一是使用大核卷积/大感受野来增强特征融合。
你可以理解成：

LCNetV4：负责提取“看到了什么”
RepLKFPN：负责把不同分辨率看到的信息整合起来
3. DB
这里才真正开始回答：

哪些像素属于文字？
DB 的核心不是直接预测 polygon。
它首先预测的是类似：
DB Head
           ↓
      Probability Map

0.01 0.02 0.01 0.03
0.02 0.80 0.92 0.85
0.01 0.88 0.97 0.91
0.01 0.60 0.72 0.65
也就是：

每一个位置属于文本区域的程度。
 DB 的核心思想是 Differentiable Binarization。
---
DBNet在训练的时候，原始训练数据只有文本框，没有像素级别概率，这是其训练的时候比较有意思的地方，
假设训练数据给了一个文本框坐标，DBnet训练时不是简单把这个框里面全标成1，而是构造一个shrink map，把真实文字向内缩，然后让模型学习：
文字中心区域 → 高分
文字边缘 → 相对低
背景 → 低分
所以训练完之后，一个字符区域可能类似：
   0.92 0.95 0.96
0.88 0.94 0.97 0.95
  0.75 0.90 0.93 0.91
     0.50 0.65
这张 map 经过阈值化、连通域/轮廓提取等后处理，就变成文字框。
---
4.DB后处理
后处理再做：
Binary Map
    ↓
Threshold （text_det_thresh=0.3）
    ↓
Connected Components / Contours
    ↓
找到轮廓 
    ↓
Polygon （det_db_box_thresh）
PaddleOCR 默认 text_det_thresh=0.3，即 score > 0.3 的像素被认为是文字像素。通过文字像素构建联通域，得到候选文字框，下一个问题，已经生成了一个候选文字框以后，这个框到底要不要保留？
PaddleOCR 会计算这个框区域里的平均 score。按照det_db_box_thresh 设定的阈值，只有平均score大于阈值的文本框才保留
所以最终：
DB 输出：
       像素级 text score

后处理：
       像素 → 连通区域 → polygon
总结：
LCNetV4 + RepLKFPN 负责把原始图片编码成适合文本检测的特征；DB Head 根据这些特征预测 text probability map；训练时使用文本标注生成的 segmentation ground truth 对这个 map 做监督。
LCNetV4 = 提取视觉特征；RepLKFPN = 融合多尺度特征；DB Head = 判断每个位置是不是文字；DB 后处理 = 把文字像素区域变成最终 polygon。

Rec阶段处理流程
Recognition 不是一次性“生成”字符串，而是先把图片变成一个“从左到右的特征序列”，然后对序列中的每个位置预测字符，最后用 CTC 把这些预测压缩成字符串。
1. Polygon → Crop：先把文字从原图里面抠出来
Detection 给文本框坐标：
Polygon = [
    (100, 50),
    (300, 55),
    (298, 90),
    (102, 85)
]
OCR 会根据这个 polygon 把文字区域裁出来。

# 文书清晰度规则检测 Pipeline
对公安、法院等机构上传的文书附件，自动下载、OCR 检测、清晰度定级、人工复核。
Pipeline 总览
输入 CSV (appid, fpath, md5)
    │
    ▼
Step 1: 下载图片        step1_download.py
    │                   → images/ 目录
    ▼
Step 2: OCR + 定级      step2_ocr_classify.py
    │                   → result.csv (含等级+指标+定级理由)
    │                   → annotated/ (OCR标注图，可选)
    ▼
Step 3: 预览复核        step3_review_server.py
                        → Web UI (图片预览 + 人工标记)
                        → reviews.json (复核记录)
最小文件集合
qingxi/scripts/clarity/
├── step1_download.py      # 下载文书图片（API → 本地文件）
├── step2_ocr_classify.py  # OCR 检测 + 清晰度定级
├── step3_review_server.py # 预览复核服务（Web UI）
└── run_xpu.sh             # XPU 运行环境包装器（加速 OCR）
输入 CSV 格式
appid,fpath,md5
0301A2002431230123900FZ2601221731310,/antiFraud/attaches/01kfjgtaeq2s8znj10829btymc,a1b2c3d4e5f6...
|列|必填|说明|
|-|-|-|
|appid|是|业务 ID，用于关联复核记录|
|fpath|是|API 路径，如 /antiFraud/attaches/xxx（公安）或 /supreme/attaches/xxx（法院）|
|md5|否|文件 MD5，用于校验下载完整性（留空则跳过校验）|

使用方法
Step 1: 下载图片
python step1_download.py input.csv ./images
- 调用下载 API http://9.147.113.141:13173/file/download，参数 bucketName=authority + destPath=fpath
- 返回 Base64 编码，按文件头自动判断格式（PDF/PNG/JPG），不做格式转换或压缩
- 下载后用 MD5 校验完整性，不匹配的标记但不删除
- 输出 images/ 目录 + images/download_report.csv 下载报告
Step 2: OCR 检测 + 定级
# XPU 加速（推荐，~0.2s/张）
bash run_xpu.sh step2_ocr_classify.py --img-dir ./images --csv input.csv --out result.csv --annotate-dir ./annotated

# CPU 模式（较慢，~1s/张）
python step2_ocr_classify.py --img-dir ./images --csv input.csv --out result.csv --annotate-dir ./annotated
对每张图：
1. RapidOCR (paddle XPU) 跑全量检测，获取每行文字的坐标 + 置信度
2. 印章排除（HSV 红色占比 > 8% 的文本行不参与定级）
3. 计算指标：加权平均置信度、最低置信度、不可辨比例（conf<0.80 的行权重占比）、拉普拉斯方差
4. 按定级规则计算等级
5. 生成带 OCR 框的标注图（绿≥90% / 黄70-90% / 红<70%）
输出 result.csv，字段：

|字段|说明|
|-|-|
|appid|业务 ID|
|fpath|API 路径|
|filename|本地文件名|
|xgb_level|清晰度等级 (1-5)|
|ocr_avg_conf|加权平均置信度 (0-100)|
|ocr_min_conf|最低置信度 (0-100)|
|ocr_total_lines|文字行数（排除印章后）|
|ocr_low_conf_ratio|不可辨比例 (0-1)|
|ocr_unclear_boxes|模糊行数 (conf<0.80)|
|ocr_laplacian_var|拉普拉斯方差（锐度指标）|
|is_seal_excluded|排除的印章行数|
|reason|定级理由（中文描述）|

Step 3: 预览复核
python step3_review_server.py --csv result.csv --img-dir ./images --annotate-dir ./annotated --port 8773
打开 http://<服务器IP>:8773/ 即可使用。

功能：
- 左侧列表：按等级排序，显示人工复核标签，支持筛选（未复核/全部/已复核）和搜索
- 右侧预览：原图 + OCR 标注框（可切换开/关），支持缩放（滚轮/双击）
- 定级理由：显示不可辨比例、置信度、拉普拉斯方差等指标和定级原因
- 人工复核：快捷键 1-5 标记等级，6 标记不确定，←/→ 翻页，U 撤销
- 导出：导出带复核结果的 CSV
定级规则
等级 1=最清晰，5=无法辨认。基于 OCR 置信度指标判定，漏检补偿已禁用。

|条件|等级|说明|
|-|-|-|
|不可辨比例 ≥ 90% 或 平均置信度 < 60|5|无法辨认|
|不可辨比例 ≥ 50% 或 平均置信度 < 75|4|大部分模糊|
|不可辨比例 ≥ 10%|3|局部模糊|
|平均置信度 < 92 或 最低置信度 < 75 或 拉普拉斯方差 < 3000|2|轻微模糊|
|以上均不满足|1|完全清晰|


指标说明：
- 不可辨比例：置信度 < 0.80 的文本行的加权占比（权重 = 0.7×字数 + 0.3×面积比×1000）
- 拉普拉斯方差：图像锐度指标，值越大越清晰
- 印章排除：红色印章上的文字不参与定级（HSV 红色占比 > 8%）
