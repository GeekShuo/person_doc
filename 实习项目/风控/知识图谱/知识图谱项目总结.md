> 基于 `知识图谱.md`、`基于本体的风控知识图谱设计.md`、`工作记录.md`、`复现记录.md`、`大模型×知识图谱新任务范.md`、`合规实体一览.md` 及 GraphSSR 论文（KDD 2026）整理。

## 一、为什么要建知识图谱——三大核心困境倒逼

### 1.1 原始数据的「不可用」状态

风控本体数据体量庞大：**113 张源表、3,128 个字段**，直接拿原始表做图会遇到三个致命问题：

**困境 1：事件类实体 ≠ 图谱边，语义不匹配**

源表中的交易类（`trade_*`）、操作类（`operation_*`）、负面类（`info_negative_*`）本质是「事件记录」，而非图谱中的「关系」。一张交易表同时隐含买家→卖家、商户→渠道、资金→账户等多条关系，直接当边用会丢失角色区分、产生大量冗余自环。每张事件表 20–60 个字段，若全量导入，单条边 4–9 KB，存储成本不可控。

**困境 2：ID 体系不统一，跨表关联断裂**

商户存在 `tenpay_merchant_id` 和 `wechat_merchant_id` 两套 ID，个人有 `account_uin` / `customer_id` / `uid` 多套标识；部分表存明文、部分存 MD5；同名不同义（`user_id` 在 A 表指微信用户、B 表指 QQ 用户）。旧版实测：**190 个端点中仅 26% 可直接 Join，其余空值率 >80% 或值域无交集**。

**困境 3：存储量级巨大，明细落地不可行**

去重 80 张源表单条字节未压缩合计 **58,768 B**；交易类按小时产出、单表日均百万–千万级行；若全量明细入库预估 **TB 级**，且绝大部分字段对反洗钱无意义。

### 1.2 业务侧的「证据链」诉求

反洗钱与反欺诈场景需要的不是单点「风险/正常」的判别，而是：
- **可审计的多跳关系证据链**（如：账户 A → 中介账户 B → 商户 C 的资金归集后拆分转出）
- **带时间约束的可疑模式识别**（短时高频、拆分交易、团伙共用设备/IP/卡）
- **风险团伙的结构化解释**（核心/中介/外围成员角色、关键共享实体）

传统特征工程能算相似度，但很难直接给出一条可审计、多跳、带时间约束的关系证据链。这正是知识图谱 + 大模型要解决的核心问题。

## 二、怎么建的——两阶段构建方法论

### 2.1 总体思路：语义分层 + 属性收敛 + 图原语重构

核心创新：**不再把所有源表平等对待**，而是按「静态实体」vs「事件实体」分两条路径建模。事件类不直接当边，而是先重构为图原语（主边/辅助边 + 聚合属性），再入图。

```
113+ 张源表 / 3,128 字段
        │
        ▼
  实体类型分类（静态 vs 事件）
        │
   ┌────┴────┐
   ▼         ▼
静态实体路径   事件实体路径
（搭骨架）    （重构为边）
   │         │
   └────┬────┘
        ▼
18 点 · 206 边 · 1,755 边属性 · 1,374 聚合属性
```

### 2.2 阶段一：静态类实体建模（搭骨架）

| 步骤 | 动作 | 产出 |
|---|---|---|
| 保留节点 | 筛出「客观存在的、不由动态交互产生」的实体：账户、设备、主体（商户/个人客）、介质（二维码/App/公众号等） | **18 类顶点**（账户 4、主体 3、介质 3、线索 8） |
| 属性评分 | 对所有字段做反洗钱相关性评分，只保留高价值属性 | **265 个点属性**（从 3,128 字段收敛，压缩率 91.5%） |
| 筛选静态边 | 识别业务含义明确且长期稳定的归属关系（法人→商户、超管→商户、上级→下级） | **30 条静态边** |
| 静态连接 | 写入图库，形成基础图谱骨架——顶点规模不再随事件增长 | 稳定拓扑 |

### 2.3 阶段二：事件类实体重构为边（核心创新）

| 步骤 | 动作 | 产出 |
|---|---|---|
| 事件转边 | 将 `trade_*` / `operation_*` / `info_negative_*` 等 **80+ 张事件表**，每条记录拆解为「谁→谁」的边，按角色前缀区分（payer/payee/sub/parent/split…） | **175 条动态边**（主边 56 + 辅助边 119） |
| 边分类 | **主边**：承载核心业务语义与聚合属性（交易金额/频次/风险标签）；**辅助边**：补充次要关系（操作行为、客诉线索等），属性精简 | 清晰的角色分工 |
| 生成聚合 | 按反洗钱场景设计聚合窗口（7d/30d），在边上计算累计金额/频次/占比/最近时间等指标 | **1,374 个聚合属性**（从早期 3,099 个收敛） |

**边的完整信息设计**（每条边 20+ 个元数据字段）：必须记录来源事件实体 `event_entity`、起终点的事件标准字段与原始字段（`from_event_field` / `from_event_field_raw`）、对应的静态顶点字段与主键（`from_vertex_field` / `from_vertex_pk`）、是否自环 `is_self_loop`（显式标注 + 人工复核 + 程序一致性校验）、边角色 `edge_role`、订单号与时间字段、属性分配规则（规则 A 挂主边 / 规则 B 挂辅助边）等。这套设计解决了「字段名不同但业务 ID 相同」的映射难题（如 `purchaser_id → payer_uin → account_uin`）。

### 2.4 关联字段范式：两阶段策略

| 阶段 | 关联口径 | 说明 |
|---|---|---|
| **阶段一 · 初始建模** | 语义关联「只要有就关联」 | 凡字段间存在业务语义对应关系即建立关联，先把潜在资金/关系链路尽量拉全、不漏。不强行统一键，靠语义把多源 ID 先连起来 |
| **阶段二 · 稳定期** | 主键归一 | 以静态实体（账户/商户/个人客/介质）的业务主键作为跨实体关联的**规范化键（canonical join key）**，动态交易/操作边统一通过静态实体主键归一，避免同一主体因多源字段口径不一而重复或分裂关联 |

该范式直接回应「ID 体系不统一」痛点：阶段一广拉、阶段二以静态实体主键收口，最终落到 18 类顶点的稳定拓扑上。

### 2.5 聚合属性的反洗钱场景收敛

聚合属性从早期的 **3,099 个收敛到 1,374 个**，原则是**只保留服务于可疑模式识别的维度**，不做「能聚合就聚合」。剔除了技术标识、长文本、静态画像（籍贯/职业/性别）、PII、卡号尾号等无 AML 含义的字段（共 1,108 个边属性不聚合）。

保留的六个反洗钱维度：

| 维度 | 聚合函数 | 识别的可疑模式 |
|---|---|---|
| 资金规模与频次 | sum / max / avg / count | 大额交易、频繁交易、**拆分（结构化）交易** |
| 时间集中度 | min / max | 首末交易时间，配合笔数识别短时高频、异常时段 |
| 介质分散度 | count_distinct | 一账户多设备/多 IP、一卡多人，**团伙与账户共用** |
| 渠道场景异常 | count_distinct / last_value | 频繁切换渠道与场景，典型规避手段 |
| 风险处置历史 | true_count / true_rate | 被拦截、被管控、被举报的次数与占比 |
| 状态变更频次 | max / count | 30 天内被评级/尽调/管控几次，频繁变更本身可疑 |

**关键工程决策**：聚合属性必须在节点降级为边的**当下就定义好**，不能等边拆完再逐条追溯——拆解后边量巨大，事后逐条补极易漏，而降级时原始实体的完整字段还在手上，此时定义最准。聚合边与明细边**并存不替代**：明细边（全部保留）用于溯源/取证，聚合边（额外生成）用于快速筛查。

### 2.6 存储测算与工程落地

- **测算工具**：`tools/estimate_volume.py` 一键生成全部 224 实体（18 顶点 + 206 边）的每日/近 30 日跑数 SQL + 字节估算，回灌 StarRocks 日计数后输出真实占用存储（GB）。
- **计量口径**：数据量 = 记录条数；占用存储 = 记录条数 × 单条平均字节（int 4 / bigint 8 / datetime 8 / string 按平均长度估值）；按未压缩上界规划，StarRocks 落地有 3–5× 压缩。
- **实测数据**（部分）：微信账户 **23.98 亿**顶点（估算 1,268.6 GB）、个人客户 **10.93 亿**、商户账户 **3.96 亿**（604.3 GB）、商户客户 1.32 亿；个人收款码 1,808.7 万（行膨胀 2.51 倍，写入图库前必须去重）。
- **图数据库**：腾讯自研 **EasyGraph**，两种写入方式——SDK `g.addV/addE`（实时，需 RocksDB 环境）与太极 `pull_sst → switch_graph_version`（批量）；管理面 MetaServer（govern.jar，端口 58610）管 schema/图空间/图版本，数据面 Gremlin Server（端口 8184）存真实点边。
- **闭环验证流程**：图谱结构设计 → 数据写入校验 → 问题归因 → 图谱结构修复 → 持续复盘重新校验。

## 三、怎么训练大模型理解解析——GraphSSR 复现与两阶段训练

### 3.1 为什么需要 GraphSSR：大模型直接读图的噪声问题

传统 GNN 在 zero-shot 场景下无法泛化到未见领域或标签空间；近期范式（Graph-R1）采用纯文本格式让 LLM 做图推理，但使用 **task-agnostic、one-size-fits-all 的子图提取策略**，不可避免地引入大量**结构噪声**——无关邻居和边会扭曲 LLM 的感受野，导致次优预测。

**GraphSSR（KDD 2026）核心思想**：自适应子图提取与去噪。通过 **SSR pipeline（Sample-Select-Reason）** 动态定制子图提取：
1. **Sample**：采样多个候选小子图（保证候选间差异显著）
2. **Select**：选择一个与任务最相关的子图（给出选择理由）
3. **Reason**：仅用选中子图推理作答

> 团队对 GraphSSR 的实质有更精准的重新定义：它不是「子图压缩」（输入仍然是大子图 G₀），而是**「任务驱动的显式证据子图选择与推理引导」**——S 不负责替代 G₀，而是帮助模型在复杂图中先明确：当前任务最应优先看的是什么关系、路径、实体和属性。G₀ 仍提供验证上下文与反证可能。

### 3.2 两阶段训练框架

**阶段一：SSR-SFT（监督微调冷启动）**
- 用教师（DeepSeek-R1-0528）生成的高质量 SSR 推理轨迹做 SFT，让模型内化完整的 Sample-Select-Reason 流程
- 学生模型：**Qwen3-8B**，full SFT，template `qwen3`，cutoff 8192，3 epochs（390 步），lr 1e-5 cosine
- 数据：8,265 条 SSR 轨迹（243MB）

**阶段二：SSR-RL（两阶段 GRPO 强化学习）**

| 阶段 | 奖励函数 | 目标 |
|---|---|---|
| **Stage 1：真实性强化** | R₁ = R_real（真实性）+ R_consist（一致性）+ R_correct（正确性），三层嵌套逻辑 | 减少子图去噪过程中的幻觉，强化基础图推理能力 |
| **Stage 2：去噪强化** | R₂ = R₁ + λ·r_size（r_size 基于组内选中子图规模的降序排名） | 引导模型用**精简的去噪子图**做出同等准确的预测 |

GRPO 的组内对比机制与 SSR 策略天然契合：同一 prompt 采样 n=4 个响应，啰嗦到被截断的拿 0 分，预算内写完的拿高分 → 优势函数给「精简且完整」的响应正优势。

### 3.3 复现的工程实现与难点攻关

**环境栈**（4×A100-40GB 单机）：llamafactory 0.9.5（SFT）+ verl 0.6.0（RL）+ vllm 0.10.1.1 + deepspeed 0.19.5（ZeRO-3）。

**版本选型的连锁约束**：驱动 535.129.03（CUDA 12.9 上限）锁死新版栈——最新 verl(0.9) 要求 vllm≥0.18 + torch 2.11/cu130（驱动不可用）；vllm 0.11+ 绑 torch 2.8/2.9（与 torch 2.7.1 冲突）；**vllm 0.10.1.1 是唯一精确绑定 torch==2.7.1 的版本**。修掉的坑包括：torchaudio(cu126) 与 torch(cu129) CUDA 检查冲突（patch 扩展工具仅比较主版本）、opencv/cupy 要求 numpy≥2（降级）、numpy 被 vllm 连带升到 2.x（钉回 1.26.4）。

**40GB 卡跑 8B full SFT 的显存组合**（试错 3 轮定型）：

| 措施 | 解决的问题 |
|---|---|
| ZeRO-3 | 参数/梯度分片 |
| **Liger Kernel**（fused CE） | 消除 `logits.float()` 的 4.64GB 峰值 |
| **优化器 CPU offload** | fp32 AdamW 状态 24GB/卡 → CPU，显存 40GB→20GB（代价：训练速度变慢） |
| `expandable_segments` | 防显存碎片 |

**RL 从 8 节点×8 卡到单机 4 卡的适配**：`train_batch_size 1024→64`、`mini_batch 64→16`、`tp 4→1`、`gpu_memory_utilization=0.7`、`max_model_len=24576`、actor/ref 全 offload。

**自动化管线**：`scripts/run_all_pipeline.sh` 实现校验 → SFT → Stage1 → Stage2 串行，每步产物检查，失败即停。

### 3.4 训练中发现的关键问题：截断 = 没分

SFT 模型从教师轨迹学到的天然输出长度是**中位 6,847 token**（90% 分位 9,604），而 RL 阶段上限设为 6,144 → **训练初期 88.3% 的响应超预算被截断**。

为什么截断是致命的：SSR 的输出结构是「先采样 → 再选择 → 最后给答案」，答案标签在最末尾。被截断 → 没写出 `<Answer>` → 正确性奖励 = 0，真实性/一致性标签也没闭合 → R₁ 几乎全扣光。

GRPO 的自纠正机制：同一 prompt 采样 4 个响应组内对比，被截断的拿 0 分，预算内写完的拿高分 → 梯度持续推向「精简且完整」。**训练结果：回答长度从初始约 6,000 下降到 3,500**，模型自发学会了精简。

## 四、达到了什么效果

### 4.1 图谱构建成果

| 指标 | 数值 | 说明 |
|---|---|---|
| 点类型 | **18** | 账户 4 / 主体 3 / 介质 3 / 线索 8 |
| 边 | **206** | 主边 56 + 辅助边 121 + 静态边 30（交易 110 / 操作 55 / 负面 13 / 静态 30） |
| 点属性 | **265** | 从 3,128 源字段收敛（-91.5%） |
| 边属性 | **1,755** | 含 1,374 个聚合属性（从 3,099 收敛，-55.7%） |
| 实测顶点规模 | 微信账户 23.98 亿、个人客户 10.93 亿、商户账户 3.96 亿 | 十亿级真实数据灌入测试集群 |
| Schema 写入 | 21 个顶点全部成功写入 EasyGraph 测试集群 `easygraph.ldbc_multi_replica` | 含 DSL 转换脚本与 sh 逐条写入 |

### 4.2 GraphSSR 复现效果（核心验证结果）

测试集：官方预生成 600 条抽样 40 条（cora 节点分类任务）：

| 策略 | 选中子图节点数 | 压缩率 | 答案准确率 |
|---|---|---|---|
| Raw Subgraph（不压缩） | 23.9 | 0% | — |
| **Stage1（R₁ 真实性强化）** | 9.3 | **61.0%** | **76.9%** |
| **Stage2（R₂ 去噪强化）** | **4.9** | **79.5%** | 75.0% |

**结论**：Stage2 在准确率基本不变（-1.9pp）的前提下，把子图从 9.3 个节点进一步压到 4.9 个——**用约 1/5 的证据做出同等准确的判断**，验证了 GraphSSR 两阶段设计的价值。实际案例中，模型从 20+ 节点的完整子图中选出 19 个节点完成作答，预测正确且全程无编造边。

训练动态：SFT 损失持续下降收敛良好、无梯度爆炸；RL Stage1 reward 提升明显，回答长度 6,000→3,500 自发精简。

### 4.3 超越节点分类：面向风控的新任务范式设计

原始 GraphSSR 只设计了三类标准判别任务（节点分类 NC / 链接预测 LP / 链接分类 LC）。团队论证了**比节点风险判别更值得做的五类下游任务**：

| 任务 | 输入 → 输出 | 图算法与 LLM 分工 | 评估指标 |
|---|---|---|---|
| **1. 风险链路追踪** | 高风险账户 + 时间窗异构交易图 → Top-K 可疑链路（标注时间/金额/关系类型/异常原因） | 图算法枚举满足时间约束的路径；LLM 从大量路径中压缩和解释最值得调查的几条 | Path Recall@K、路径边 Precision、时间合法率、分析师采纳率 |
| **2. 风险团伙发现与成员归因** | 告警种子 + 账户—设备—IP—商户—交易异构图 → 疑似团伙成员集合 + 核心/中介/外围角色 | 图算法产生社区/k-core/共享设备簇/motif 候选；LLM 判断业务意义、去掉热门商户/公共 IP 假连接、解释团伙结构 | 团伙 Pairwise-F1、成员 Recall@K、发现提前量、人工复核工作量 |
| **3. 告警证据包生成** | 已有告警 + 上下文大图 + 调查问题 → 预算内证据包（关键实体/边/2–3 条风险链路/风险模式/调查结论） | 最契合「子图压缩」主任务：把巨大调查上下文压缩为可审核证据 | 证据完整性、token 预算内信息密度 |
| **4. 风险关系/隐性关联判别** | 实体 A 与 B → 是否存在可疑关联及类型（共享设备/资金中转/受益人穿透/控制关系/团伙共现） | 特征工程难给出可审计、多跳、带时间约束的关系证据链 | 关系类型准确率、证据链可解释性 |
| **5. 新型风险模式发现与变化追踪** | 相邻两个时间窗的图 Gt-1 → Gt → 新形成的关系模式/资金团/共享实体结构 | 发现规则尚未覆盖的新攻击方式 | 早发现时间、已知案件覆盖率、误报量 |

### 4.4 范式认知升级：从 SFT 到 Agentic RL × KG

团队在探索中系统梳理了 KG × LLM 的范式演进：

| 范式 | 谁决定「查什么」 | LLM 干什么 | 训练方式 | 局限 |
|---|---|---|---|---|
| **GraphRAG** | 固定 pipeline（embedding/fan-out） | 读检索上下文 → 生成 | 多为推理 | 非 Agent，检索策略僵化 |
| **GraphLLM** | 图引擎（扩散/剪枝） | 读 Graph2txt → 判别 | SFT | Prompt 太长易丢图结构；SFT 只是模仿样本说话，无法真正训练判读/解释/干预策略能力 |
| **GNN + LLM** | 图引擎/GNN 邻域 | GNN 编码结构注入 LLM | 联合微调/LoRA | 跨模态对齐问题 |
| **Agentic RL × KG**（探索方向） | **模型自己** | 多轮「思考 → 查图 → 观察 → 再思考」 | **RL 优化整条查图轨迹** | 需精心设计图环境与 reward |

Agentic RL × KG 的核心：把知识图谱从静态检索库变成 **LLM Agent 可交互的环境**。对风控场景，输出从「答案实体」改成「风险结论、可疑主体或证据路径」（参考 KG-R1 的单 Agent 多跳组合、Graph-R1 的「何时检索、检索什么、何时停止」）。

## 五、技术深度与难点总结

### 难点 1：海量异构数据的图原语重构（数据工程深度）

不是简单的「表=点、记录=边」朴素映射，而是需要：
- **语义分层**：区分静态实体与事件实体，事件类降级为边时保留完整的来源血缘（`event_entity` + 原始字段 → 标准字段 → 顶点字段的三级映射）
- **属性收敛的判断力**：3,128 字段 → 265 点属性，1,108 个边属性明确不聚合，每一个取舍都需要反洗钱业务语义支撑
- **聚合属性的前置定义**：必须在节点拆解为边的当下定义，事后追溯不可行
- **行膨胀处理**：如个人收款码行膨胀 2.51 倍（4,537 万行明细 → 1,808 万顶点），写入前必须 ROW_NUMBER 去重

### 难点 2：ID 体系不统一下的跨表关联（数据治理深度）

190 个端点仅 26% 可直接 Join 的现实下，设计「阶段一语义广拉 → 阶段二主键归一」的两阶段范式，用静态实体业务主键作为 canonical join key 收口，保证关联结果稳定可复现。字段名不同但业务 ID 相同的映射（`purchaser_id → payer_uin → account_uin`）需要逐字段人工对齐 + LLM 辅助评判。

### 难点 3：十亿级规模的存储与工程落地（系统工程深度）

- 精确的存储测算体系（逐实体 bytes_per_row 估算 + 每日/30 日滚动窗口 SQL 自动生成）
- EasyGraph 双写入通道（SDK 实时 vs 太极 SST 批量）与 MetaServer/Gremlin Server 管理面/数据面分离架构
- DUPLICATE KEY 表的去重取最新、分桶策略（HASH × 24/120）、30 天分区保留、hour/day 级更新频率的差异化设计

### 难点 4：受限资源下的 8B 模型全参数训练（训练工程深度）

- 驱动 CUDA 12.9 上限锁死整个依赖栈，vllm 0.10.1.1 是唯一可行版本的连锁推理
- 40GB 单卡跑 8B full SFT：ZeRO-3 + Liger Kernel fused CE + 优化器 CPU offload 的组合拳（显存 40GB→20GB）
- 64 卡配置 → 4 卡适配的批量/并行度/显存利用率全参数重调

### 难点 5：RL 训练中的奖励设计与截断困境（算法工程深度）

- 三层嵌套奖励 R₁ = 真实性 + 一致性 + 正确性，任何一环因截断未闭合就全扣光
- 88.3% 初期截断率下，GRPO 组内对比机制如何让模型自发学会「精简且完整」（回答长度 6,000→3,500）
- Stage2 去噪奖励 r_size 基于组内规模排名，λ 需精心校准：过小无去噪效果，过大过滤关键信息
- 去噪效果的验证不能看 reward 曲线，而要看**实际选出子图的节点数**（23.9 → 9.3 → 4.9）

### 难点 6：从学术任务到风控业务的鸿沟跨越（任务设计深度）

原始 GraphSSR 的 NC/LP/LC 全是判别类学术任务，与风控的「风险链路、团伙挖掘、证据包生成」存在本质差异。团队提出五类新任务范式，并明确图算法与 LLM 的分工边界：**图算法负责枚举/候选生成（路径、社区、motif），LLM 负责压缩、解释、去伪存真**——不重复造图算法的轮子，而是让大模型做它最擅长的语义判断与证据组织。
