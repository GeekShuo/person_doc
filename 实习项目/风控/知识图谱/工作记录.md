### 1.规范schema边的生成原则

之前我们的边都是由外键和主键关联构成的，“关联边和关系名“这张表内的边都是这样生成的。

但是根据上周的点边转换规则的更新（

Stage1--事件顶点重构为边转换准则--Schema

），我们的交易/操作/部分info类型需要被降级重构为各种类型的边，这种边和之前外键依据构成的边完全不一致

需要经过以下流程：  
（1）先把原来的表里面的有关交易/操作/部分点边的边去除

（2）把剩下的静态实体之间的边来进行分类，通过LLM+人工判断有哪些边是有实际业务含义的，并给出命名，然后有哪些边是需要舍弃的

这里的工作量主要体现在，静态实体之间本来没有业务联系，所以如果要保留这种边，需要人工对齐该边的具体含义，以及连接的依据（默认是按外键相同连接的）

（3）将交易/操作/部分info类型节点降级为具体边，并且和静态实体保留的关系边合并。合并的时候需要设计去重策略，观察是否有重复的边

注意，这种降级生成的具体边，涉及的实体仍然是**静态实体，只是连接的依据不再是外键相等就连接，而是根据具体的原来的交易类设计涉及的实体进行连接（需要）** 所以构建这种边的DSL的时候，我们应该要设计从原来的实体里面抽取对应的涉及的实体，而这种涉及的实体就是根据它们原来表里面的字段，所以这种边的DSL需要**在降级的时候就构建好**，不像静态实体的边，可以根据字段相等构建

（以上都基于一个前提，

是否要多建边？(从交易/操作节点重构为边后，出现两个实体间有不同边的问题）

### 4.Agentic RL×KG范式探索

主要聚焦于对模型进行Agentic RL训练，让模型学会使用KG来查询到自己想要的东西

Agentic RL × KG 的核心是：把知识图谱从静态检索库变成 LLM Agent 可交互的环境。Agent 不再一次性拿固定子图，而是在推理过程中多轮执行「思考 → 查图 → 观察 → 再思考」，并用强化学习优化整条查图轨迹。

KG-R1 更适合已有二元知识图谱：图由三元组构成，系统提供 1-hop API，如查某实体的出边关系、沿某关系找邻居等。Agent 通过多轮 hop 组合出多跳路径，最终回答实体型问题。它的价值在于用单 Agent 替代人工设计的多模块 KGQA 流水线，并提升跨图迁移能力。

Graph-R1 则偏 GraphRAG 场景：先从文档构建知识超图，再让 Agent 在超图上多轮检索相关事实，最后生成答案。它强调用 RL 学会何时检索、检索什么、何时停止。

总体来看，这类方法的本质是：人设计图环境和 reward，模型学习用图策略。对风控等场景，可将输出从「答案实体」改成「风险结论、可疑主体或证据路径」。

### 4 Schema点，边构建范式工作与难点探索

首先，建立了新的图空间fit_demo_new，并且把所有原来的节点给写入进了Schema内

接下来的任务是把节点的属性写入&把边写入

节点属性写入暂时选择是只写入关联字段，其他字段选择性写入，边属性还没确定，都需要结合具体业务场景来核定。

而Schema构建过程中，出现了争议性比较大的疑点：

schema

**疑问 1：相似边感觉冗余**

很多交易类或信息类的边，它们连接的实体几乎都是同一类实体。比如主键都是 `app_id` 的小程序、公众号、APP、域名、==企业微信==——这 5 种商户应用，关联的商户账户完全一样，只是应用类型不同。

**疑问 2：交易类能不能不做成实体节点，而是做成边？**

交易类实体（trade_xxx）本质上是两个账户之间的交易行为，可能不需要单独做顶点，直接做成两个账户之间的边，把交易属性挂在边上。

**疑问 3：非交易类但本身也是行为类的实体（操作行为）该做成边还是具体实体节点？**

操作行为类（operation_xxx）如绑卡、改密码、司法查冻扣——它们该做成实体节点，还是也能做成边？

**疑问 4：保留交易做顶点，"交易→账户"的边上的属性设什么？**

交易做成顶点后，它和账户之间的边表达什么？边上带什么属性？

**疑问 5：如果交易做边而不是节点，多笔交易在两个账户间能不能聚合。设计主边->展开边（主schema-子schema）结构**

如果交易做边，两个账户间有很多条交易边，能不能聚合？有没有"主边-子边"（主schema-子schema）的设计？

**疑问 6：字段转换时怎么处理**

每次从顶点转成边/属性/合并时，原来的字段怎么办？

要进行对齐，对Schema的构建设计一个全面，可供解释的方案，暂时拟定了一版方案，并且针对表内的各个实体进行分类（是否要化为边，是否要转化为节点）
