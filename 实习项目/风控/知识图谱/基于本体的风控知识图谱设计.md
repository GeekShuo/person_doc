## 建模逻辑方法论

### 一、现有明细数据的关联与存储困境

本体数据体量庞大（113 张源表 / 3128 字段），直接拿原始表做图会遇到以下核心困难：

#### 困难 1：事件类实体 ≠ 图谱边，语义不匹配

|问题|说明|
|---|---|
|实体类型混淆|源表中 **交易类**（trade_*）、**操作类**（operation_*）、**负面类**（info_negative_*） 本质是「事件记录」，不是图谱中的「关系」。|
|一行多关系|一张交易表同时包含 买家→卖家、商户→渠道、资金→账户 等多条隐含关系， 直接当边用会丢失角色区分、产生大量冗余自环。|
|属性爆炸|每张事件表 20–60 个字段，大部分与反洗钱无关。 若全量导入图谱边，单条边 4–9 KB，存储成本不可控。|

#### 困难 2：ID 体系不统一，跨表关联断裂

|问题|说明|
|---|---|
|同一实体多键|商户有 `tenpay_merchant_id` 和 `wechat_merchant_id` 两套 ID， 个人有 `account_uin` / `customer_id` / `uid` 多套标识， 不同表的关联键可能指向同一实体的不同编码。|
|值域不通|部分表存明文 ID，部分存 md5 加密值；同名不同义（如 `user_id` 在 A 表指微信用户、B 表指 QQ 用户）。|
|空值率高|旧版实测：190 个端点中仅 26% 可直接 Join，其余空值率 >80% 或值域无交集。|

#### 困难 3：存储量级巨大，按明细落地图不可行

|维度|数据|
|---|---|
|源表总字段|3,128 字段 × 113 表|
|日增量级|交易类按小时产出，留存 30 天；单张交易表日均百万–千万级行|
|未压缩上界|去重 80 张源表，单条字节合计 **58,768 B**； 最大单表履职尽调类约 8–9 KB/行|
|若全量明细入库|预估 TB 级，且绝大部分字段对反洗钱无意义|

**结论**：113 张原始表不能按「表=点、记录=边」的朴素方式直接建模入图—— 事件类记录与图关系语义不同、跨表 ID 体系不统一、全量字段冗余且量级巨大， 直接落地将带来**存储成本失控**与**关系语义失真**。 因此须先**语义分层**（静态实体 vs 事件实体）、**属性收敛**（仅保留反洗钱高价值字段）， 再**重构为图原语**（顶点 + 边 + 聚合属性），方可在工程上稳定落地。

### 二、新构建思路：将实体类型分类，重构事件类实体为边再构图

核心创新：不再把所有源表平等对待，而是按「静态实体」vs「事件实体」分两条路径建模， 事件类不直接当边，而是先重构为图原语（主边/辅助边 + 聚合属性），再入图。

|新版图谱结构|静态骨架 + 动态事件边 + 聚合属性 = **完整可查询的知识图谱**|18 点 / 206 边 / 1,755 边属性|

#### 关联字段范式规则（两阶段）

|阶段|关联口径|说明|
|---|---|---|
|**阶段一 · 初始建模**  <br>语义关联|「只要有就关联」|凡字段间存在业务语义对应关系即建立关联，先把潜在资金 / 关系链路尽量拉全、不漏。对应上文「困难 2：ID 体系不统一」——初期不强行统一键，靠语义把多源 ID 先连起来。|

该范式直接回应「ID 体系不统一」痛点：阶段一广拉、阶段二以静态实体主键收口，最终落到 18 类顶点的稳定拓扑上。

### 三、存储数据量与占用存储测算

新思路解决了「属性爆炸」问题（3,128 字段 → 265 点属性 + 1,755 边属性）， 但落地前仍需精确测算每个实体的每日/每30日 数据量与存储占用。以下是测算口径与可直接跑的代码。

**计量口径**

- **数据量** = 记录条数（rows）；按实体（顶点 / 边）分别统计。
- **占用存储** = 记录条数 × **单条平均字节 bytes_per_row**； bytes_per_row 由各字段 `est_bytes` 求和得到（entity_fields.csv 已估算： int 4 / bigint 8 / datetime 8 / float 4 / double 8，string|varchar 按平均长度估值）。
- 该值为**未压缩上界**；StarRocks 落地有压缩（约 3–5×），按上界规划容量更稳妥。

**partition_date 格式**：字符串时间戳 `2026-08-03 17:00:00`（ISO 格式）。

- 按天分桶：`to_date(partition_date)` 或 `substr(partition_date,1,10)` → `2026-08-03`。
- 字符串按字典序可直接比较，筛选范围用 `partition_date >= concat(date_sub(current_date(), INTERVAL 29 DAY), ' 00:00:00')`。

#### 时间窗口口径

- **每日**：按 `to_date(partition_date)` 分组得 `rows_day`。
- **每30日**：滚动近 30 天，用窗口函数 `SUM(rows_day) OVER (ORDER BY dt ROWS BETWEEN 29 PRECEDING AND CURRENT ROW)` 得到 `rows_30d`（看趋势）；同时 × bytes_per_row 得 `bytes_30d`。

#### 跑数代码 ①：单实体 每日 + 近30日（StarRocks）

-- 实体: <实体名>  源表: <源表>  单条字节≈<bytes_per_row>
-- partition_date 格式: '2026-08-03 17:00:00'（字符串时间戳）
WITH daily AS (
  SELECT to_date(partition_date)                          AS dt,
         COUNT(*)                                          AS rows_day
  FROM <源表>
  WHERE partition_date >= concat(date_sub(current_date(), INTERVAL 29 DAY), ' 00:00:00')
  GROUP BY to_date(partition_date)
)
SELECT
  '<实体名>'                                            AS entity,
  dt,
  rows_day,
  SUM(rows_day) OVER (ORDER BY dt ROWS BETWEEN 29 PRECEDING AND CURRENT ROW) AS rows_30d,
  rows_day * <bytes_per_row>                               AS bytes_day,
  SUM(rows_day) OVER (ORDER BY dt ROWS BETWEEN 29 PRECEDING AND CURRENT ROW) * <bytes_per_row> AS bytes_30d
FROM daily
ORDER BY dt;

### 聚合属性已按反洗钱场景收敛

聚合属性从早期的 **3099** 个收敛到 **1374** 个。原则是**只保留服务于可疑模式识别的维度**， 不做「能聚合就聚合」。剔除了技术标识（guid/archive_path）、长文本、 静态画像（籍贯/职业/性别）、PII（姓名/地址）、卡号尾号等无 AML 含义的字段。

#### 保留的六个反洗钱维度

|维度|聚合函数|识别的可疑模式|
|---|---|---|
|资金规模与频次|sum / max / avg / count|大额交易、频繁交易、**拆分（结构化）交易**|
|时间集中度|min / max|首末交易时间，配合笔数识别短时高频、异常时段|
|介质分散度|count_distinct|一账户多设备/多IP、一卡多人，**团伙与账户共用**|
|渠道场景异常|count_distinct / last_value|频繁切换渠道与场景，典型规避手段|
|风险处置历史|true_count / true_rate|被拦截、被管控、被举报的次数与占比|
|状态变更频次|max / count|30 天内被评级/尽调/管控几次，频繁变更本身可疑|

|项|规则|
|---|---|
|点的判定|有稳定唯一身份、可被指向。分四类： 账户 4、主体 3、 介质 3（银行卡/设备/手机号）、 线索 8（二维码/APP/小程序/公众号/域名/企微）|

|辅助边|主边两端外的**每个外键字段各自成边**。 同一顶点被多字段指向时（如退款表 8 个商户号）必须逐字段建边，否则丢关联|
|自环边|只有 1 类端点顶点的事件表，本版全部保留|
|边属性归属|非外键字段全部挂主边（或自环边）； 辅助边与静态边只表达关联存在性，不带属性|
|聚合口径|30 天窗口，命名 `{字段}_{函数}_30d`，按反洗钱六维度筛选|
|时间轴|优先业务时间字段；无业务时间的退回 `partition_date`（精度到天）|
