模糊样本

一、数据痛点分析

1.1 审核数据总览

2026 年 1 月 - 6 月人工审核共发现 200+ 条 bad case。归因分析后收敛为三大类根因：

根因大类占比说明

A · 文书本身模糊~70%扫描不清、拍照虚焦、公章/水印遮挡、部分字过小导致字符不可辨

B · 文书格式不规范~20%横排两页、多列布局、二维码/水印插入、字段位置漂移

C · 相近字符识别错~10%视觉相似字符高频混淆，OCR 模型能力上限

1.2 三大痛点详解

A · 文书本身模糊（~70%）

文书成像质量差是最主要的错误来源。审核中反复出现的具体现象：

- 公章遮挡：公章覆盖账号字符，0 被识别成 8
- 水印切断："2026" 水印插入账号中间：L139\n2026\n89353887
- 字体模糊：扫描分辨率不足、传真件二次成像，字符边缘断裂
- 部分字过小：账号/文号等关键字段字号过小，扫描/压缩后字符粘连或断裂
- 边缘丢字：字符太靠近页面边缘被裁掉（h→n、u→i）
- 字体怪异：手写体、艺术字体、褪色字迹识别错误
- 背景干扰：底纹/纹路污染字符边缘

典型案例：公章影响，字符0识别成字符8、水印影响，导致账号字符串被分割开、字符太靠近边缘识别错误

B · 文书格式不规范（~20%）

文书排版不符合标准模板，OCR 按默认阅读顺序输出导致字符串错乱：

- 横排两页扫描：两页横向拼贴，OCR 按 y 坐标从上到下扫，账号被两页交错拼接
- 公章位于账号中间：公章插入账号字符串，OCR 把公章文字与账号混排
- 二维码插入：二维码位于账号旁边，字符串被切断
- 相邻字段污染：账号字符串中间没有空格或标点，与相邻字段（如"查询线索"）之间没有明显分隔，OCR 无法识别字段边界，把相邻字段的字符插入账号中间
- 侧边材料入镜：键盘/其他材料文字被识别并插入账号
- 字段位置漂移：不同派出所模板差异大，同一字段在不同位置

典型案例：文书有两页，横着摆放，OCR识别按照从上到下的顺序识别文字，导致账号错乱（出现 3 次）

C · 相近字符识别错（~10%）

这不是随机错误，而是几对固定的"死亡组合"反复出现，说明是模型对特定字符对的分辨能力上限：

混淆对出现频次典型案例

b ↔ t15+ 次bb 后缀 → tt

e ↔ 65+ 次085e9858e → 08569858e

f ↔ 1 / l高频ff → 11、f → Г

7 ↔ 1 / 2高频数字位混淆

0 ↔ 8中频常受公章影响

a ↔ 8中频字体变形

n ↔ r中频n → r 导致判断错误

Z ↔ 2低频大写字母

vv ↔ w低频连续字符误合并

rn ↔ m低频连字符误合并

5/3 ↔ :低频形状相似

其他伴生问题：

- 漏字符：连续字符去重（55→5, ff→f），窄字符（1/l/i）漏识别
- 多字符幻觉：多识别 l/k/+/| 等符号

典型案例：字符b识别成字符t、字符e识别成字符6、漏识别字符5（555识别成55）

1.3 关键洞察

- A 类（模糊）：需要在图像层面解决 —— 提升清晰度检测能力 + 去除干扰层
- B 类（不规范）：需要在版面层面解决 —— 版面分析 + 阅读顺序重建
- C 类（相近字符）：需要在后处理层面解决 —— 混淆矩阵纠错 + 格式校验反推

单靠升级 OCR 模型只能解决部分 C 类，A 和 B 需要在 OCR 之前和之后加防线。这也是重构整体架构的根本原因。

二、整体架构

2.1 架构演进

原有流程：文件 → OCR → 大模型抽取要素 → 校验

问题：所有文件走同一条链路，模糊的和清晰的、规范的和不规范的、简单的和困难的都一视同仁，导致：

- 90% 的算力浪费在简单 case 上
- 困难 case 缺乏专项处理，只能靠大模型硬吃

新架构：分层过滤 · 按需处理 · 逐层拦截

三、核心处理流程

Step 1 · 格式判断

目标：判断入参是 PDF 图片 破损文件，分流处理。

处理逻辑：

- 扩展名 + 魔数字节双重判断（防扩展名伪造）
- PDF 分流：PyMuPDF get_text() 提取文本层
      - 有文本层（字符数 > 50）→ 文本型 PDF，直接抽取，跳过 OCR
      - 无文本层 → 扫描型 PDF，走完整流程
- 图片：直接进入 Step 2
- 破损文件：无法打开 / 解码失败 → 拒绝并返回错误码

输出：标准化的图像数组 + 元数据

Step 2 · 清晰度检测（现有方案）

目标：拦截 A 类痛点中"整体模糊"的文件。

处理逻辑：

- 直接复用现有 v6_clip 模型（AUC 0.99）
- 阈值分层：
      - 清晰度 ≥ 0.7 → 放行
      - 0.3 ≤ 清晰度 < 0.7 → 送 Step 3 但降级处理（增强预处理）
      - 清晰度 < 0.3 → 直接拒绝，返回"文书模糊"错误

输出：clarity_score + is_clear

Step 3 · 版面分析 + 干扰剥离

目标：核心解决 A 类（公章/水印/二维码干扰）+ B 类（阅读顺序错乱）。

3.1 干扰层剥离

按顺序检测并剥离：

干扰类型检测方法处理

公章HSV 红色通道分离 + 形态学生成掩码 → 单独送 Seal OCR

水印频域 FFT + 颜色阈值Inpainting 修复

二维码OpenCV QRCodeDetector整块抹白

表格PP-StructureV3 table 检测单独走表格识别

处理后得到干净的主文本层送到下一步。

3.2 版面分析（PP-StructureV3）

识别文档结构元素：title text_block seal signature figure / table

3.3 阅读顺序重建

账号换行，页面折叠等问题

Step 4 · 要素定位

目标：定位文书四大关键要素的位置。

四大要素：

要素说明用途

文书抬头页面顶部的发文机关名称（如 XX 市公安局 XX 分局）与印章文字交叉校验

文书标题文书类型（如"协助冻结财产通知书"）文书分类锚点

文书账号微信 wxid tenpay 银行卡 / 身份证等核心识别目标

文书印章红色公章位置印章文字识别 + 真伪校验

文书案号文书案件号判断是否真实有效案件

双路径策略：

- 模板匹配（Fast Path，覆盖 70% 常见版式）
      - 冻结文书 / 警官证 各预定义一套 YAML 模板
      - 用文书标题作为锚点做仿射变换对齐
      - 直接根据模板中的相对坐标定位四大要素 bbox
      - 命中即返回，耗时 <100ms
- 通用抽取（Slow Path，兜底 30% 非常规版式）
      - 用 PP-StructureV3 得到的 region 结果
      - KV 匹配："被冻结人"→ 右侧文字、"账号"→ 下方文字

输出：{header_bbox, title_bbox, account_bbox, seal_bbox}

Step 5 · OCR 识别

目标：对定位到的要素区域做文字识别。

两条子链路：

场景模型处理对象

通用文字PP-OCRv5（未来做领域微调）抬头、标题、账号

公章文字PP-OCRv4 seal 产线（弯曲文字专用）印章

单次识别即可，后续通过纠错和多模型投票兜底提升准确率。

Step 6 · 字符纠错 + 模糊匹配

目标：核心解决 C 类痛点（相近字符混淆），并支持账号比对场景。

6.1 字符纠错（三层策略，由强到弱）

层 1 · 校验位反推（强约束）

- 银行卡 → Luhn 校验
- 身份证 → 校验位 + 地区码 + 出生日期
- wxid → wxid_ 前缀 + 长度 + 字符集
- tenpay → 32 位十六进制 + 常见前缀 085e9858e

层 2 · 格式约束（中约束）

- 银行卡纯数字：字母替换为形似数字（B→8, O→0, l→1）
- 微信支付纯 hex：非法字符替换为最近 hex 字符
- Beam Search 枚举候选组合，验证器打分

层 3 · 混淆矩阵替换（弱约束）

- 基于 200+ bad case 统计的字符混淆矩阵
- 对低置信度字符生成 top-k 候选
- 候选交给上层约束筛选

纠错案例：

OCR 原始: 0858985870dd4acc6efaTabb (长度 24)
校验: 长度错（应 25）+ T 在数字环境不合理
纠错: pos22 T→1 · 补齐长度
结果: 085e9858e70dd4acc6efa1abb (长度 25 ✓)
前缀匹配: 085e9858e ✓

6.2 模糊匹配（账号比对场景）

即使经过纠错，OCR 结果仍可能与入参有 1-2 字符差异（如漏字符、边缘误识别）。通过模糊匹配容忍此类偏差：

匹配算法：

- 编辑距离（Levenshtein）：允许 ≤ N 个字符差异
- 动态阈值：
      - 账号长度 ≤ 15 → 允许编辑距离 ≤ 1
      - 账号长度 16-25 → 允许编辑距离 ≤ 2
      - 账号长度 > 25 → 允许编辑距离 ≤ 3
- 权重差异：混淆矩阵中的常见混淆对（如 b↔t）编辑距离权重 0.5，其他字符权重 1.0
- 子串匹配：入参账号是 OCR 结果的连续子串（或反之），可判为匹配（应对漏字符/多字符）

匹配案例：

入参: Li1585875
OCR 结果: Li585875 (漏识别一个 1)
编辑距离: 1 ≤ 阈值 1 → 匹配成功 ✓

Step 7 · 结构化校验

目标：字段级和文档级的一致性校验。

校验类型示例

完整性冻结文书必需 8 字段全在

格式身份证 18 位 + 校验位、日期合法

逻辑冻结起止日期 start<end、期限 ≤ 6 月

交叉一致印章文字 = 发文机关、性别 = 身份证性别位

置信度任一必需字段 conf<0.7 → 复核

输出决策：

- 全部通过 且 置信度 ≥ 0.9 → AUTO_PASS
- 部分低置信度或校验失败 → 送 Step 8 多模型投票
- 严重问题（校验位错、逻辑矛盾）→ HUMAN_REVIEW

Step 8 · 多模型投票兜底

目标：处理 <10% 的低置信度或校验失败 case，通过多模型交叉验证得到可信结果。

触发条件：Step 7 判定为置信度不足或校验失败

投票模型池：

模型特点权重

PP-OCRv5主 OCR 模型，精度高1.0

RapidOCR现有生产模型，稳定性好0.8

多模态 LLM（Hunyuan / GPT-4V）语义理解强，抗干扰1.2

投票流程：

1. 三个模型分别对不确定字段做识别
2. 用 Needleman-Wunsch 序列对齐 做字符级对齐
3. 每个字符位置加权投票，权重来自模型 + 置信度
4. 三模型一致 → 直接采纳
5. 两个一致、一个不同 → 采纳多数派，标记为中置信度
6. 三个都不同 → 送人工复核

投票案例：

PP-OCRv5: 085e9858e70dd4acc6efa1abb conf 0.85
RapidOCR: 085e9858e70dd4acc6efa1abb conf 0.78
LLM: 085e9858e70dd4acc6efa1abb ← 从图像+候选中选择
一致性: 3/3 → 高置信度采纳 ✓

四、关键技术专项

4.1 账号识别专项管线

账号识别是 bad case 集中爆发点（80%+ 错误涉及账号），走专项流程：

账号区域候选 (来自 Step 4)
→ 1. 干扰层剥离（用 Step 3 生成的掩码）
→ 2. 高分辨率再采样（放大到 600 DPI 等效）
→ 3. PP-OCRv5 单次识别
→ 4. 上下文合并（跨行片段拼接）
→ 5. 字符纠错（混淆矩阵 + 格式约束）
→ 6. 校验位/长度验证
→ 7. 模糊匹配（编辑距离 + 子串匹配）
→ 8. 低置信度走 Step 8 多模型投票

账号格式知识库：

类型格式特征校验能力

银行卡15-19 位数字Luhn 校验 + BIN 前缀

身份证18 位（末位可 X）校验位 + 地区码

wxidwxid_ + 14 位前缀 + 长度 + 字符集

tenpay32 位 hex长度 + 字符集 + 前缀

QQ5-11 位数字长度 + 首位非 0

手机号11 位，1[3-9] 开头号段字典

4.2 字符混淆矩阵纠错

基于 200+ bad case 统计的混淆矩阵：

ConfusionMatrix[真实字符][识别字符] = P(识别成 j | 真实是 i)

例：
P("b" 识别成 "t") = 0.15
P("e" 识别成 "6") = 0.05
P("f" 识别成 "1") = 0.08

使用方式：

- 对每个低置信度字符 c，生成 top-k 混淆候选
- 结合上下文约束（字符集、格式、位置）筛选
- Beam Search 得到最优候选组合

4.3 输入侧清洗

针对入参脏字符问题：

def sanitize_input(s: str) -> str:

# 特殊横线归一化

# 全角转半角
s = full_width_to_half_width(s)
return s.strip()
