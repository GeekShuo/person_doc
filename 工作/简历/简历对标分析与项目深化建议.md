5. **问题类型丰富**：长尾分类、难例挖掘、软标签、OCR 结构解析、多模型融合、规则系统。

## 3.2 当前短板

### 短板 1：腾讯段项目很多，但缺少统一技术架构

目前四个子任务像四个独立需求。应呈现为统一的文档有效性校验系统：

```text
输入质检 → 方向/版面恢复 → OCR/字段理解 → 印章与类型判定
→ 号码一致性校验 → 置信度路由 → 人工/VLM 复核 → 难例回流
```

这样能体现你不是分别做四个小需求，而是在搭建一条可扩展的文档智能决策链路。

### 短板 2：清晰度项目方法新，但缺少结果

当前只描述了五级标签、软标签、LoRA、CE/KL 和期望校准，没有写：

- 相比 XGBoost 或硬标签分类提升多少；
- 五级 Macro-F1 / QWK / MAE / SRCC；
- 与人工评分的一致性；
- 对下游 OCR CER/WER 的相关性；
- 每档覆盖率和误判成本；
- 推理延迟与线上覆盖率。

没有这些结果，招聘者会把它看成“方案正在做”，而不是完成的算法成果。

### 短板 3：Guard 项目只显示“规模”，没有显示“难度”

89 万或 100 万数据本身不是最重要的。更关键的是：

- 标签体系怎样设计；
- 如何解决类别长尾和边界样本；
- 多模型投票如何校准；
- 数据泄漏、重复和近邻污染如何处理；
- SFT 与 GDPO 分别带来多少增益；
- 如何控制误杀、漏检和格式稳定性；
- 在分布外、对抗样本、多轮上下文中是否稳定。

### 短板 4：Agent 项目停留在 2023～2024 年常见表述

“Multi-Agent + RAG + Tool-Calling + 异步并行”已经不足以体现先进性。现在更重要的是：

- 长程状态管理；
- 可验证执行；
- 动态重规划；
- 失败恢复；
- 工具权限治理；
- 真实 Benchmark；
- 成本和成功率；
- 人在回路和安全审计。

### 短板 5：缺少对照实验和消融

简历中多个优秀数字缺少参照对象。例如：

- `F1 > 85%`：相对基座模型、SFT 模型还是旧系统？
- `Accuracy 99.99%`：独立测试集还是多轮调参数据？
- `Precision 100% / Recall 98.94%`：自动处理覆盖率是多少？
- `高质量数据产出率 86%`：相对旧规则提升多少？抽检规模多大？

建议所有核心数字补齐“数据集—基线—指标口径—提升幅度”四要素。

### 短板 6：缺少外部可验证成果

其他简历有论文、开源仓库、项目主页或正式比赛结果。你的项目多为内部业务，建议至少补一项：

- 脱敏技术报告；
- 文档质量评估 Benchmark；
- 通用数据清洗工具开源；
- Agent 评测框架开源；
- 专利/软著；
- 公开比赛或论文投稿。

## 四、Guard 项目还能深入哪些技术

## 4.1 当前技术发展方向

内容安全 Guard 正从“固定类别分类器”向以下方向发展：

1. **Policy-conditioned / Policy-adaptive Guard**：把自然语言政策和内容共同输入，而不是把标签固化在权重中。ShieldGemma 2 和 2026 年的 Shieldstral 都体现了这一趋势。
2. **多模态统一审核**：同时理解图片内容、OCR 文本、用户问题和模型回复，避免只做单图分类。
3. **风险分级而非二分类**：输出安全、争议、高风险或风险严重度，支持差异化处置。
4. **流式审核**：生成过程中按 token 或片段检测，而不是输出完成后再拦截。
5. **对抗数据生成与难例闭环**：系统构造边界样本、隐式表达、图中文字、风格化和多轮上下文样本。
6. **选择性分类**：高置信自动处理，中间区间交给更强模型或人工，直接优化覆盖率—风险曲线。

## 4.2 对你的项目最值得做的升级

### P0：从固定分类升级为政策条件化审核

#### 怎么做

- 将现有数十类风险整理为层级 Taxonomy：一级风险、二级场景、严重度、处置动作。
- 输入从 `图文 → 标签` 改为 `图文 + 政策定义 → 是否违反/严重度/证据区域`。
- 为每条政策保留版本号、正反例和边界说明。
- 构造“同一内容、不同政策”的对照数据，验证模型是否真的理解政策，而非记忆视觉特征。

#### 应做实验

- 固定标签分类 vs. 政策条件分类；
- 未见过政策表述的 zero-shot 泛化；
- 政策同义改写稳定性；
- 政策冲突和多政策同时命中；
- 中文、英文及中英混合政策的一致性。

#### 可形成的成果

- Policy Adaptation Accuracy；
- 新政策冷启动所需样本量；
- 政策更新后无需全量重训或仅需小规模微调；
- 可写成“政策可配置多模态安全模型”。

### P0：把数据闭环升级为“主动学习 + 不确定性采样”

#### 怎么做

不要只靠随机抽样和关键词合成。对线上数据计算：

- 模型熵；
- 多模型分歧；
- 不同增强视图的一致性；
- 近阈值样本；
- 新聚类簇和分布漂移；
- 误杀/漏检业务成本。

用这些信号决定哪些样本进入人工标注、教师模型复核和下一轮训练。

#### 应做实验

比较随机采样、置信度采样、多模型分歧采样和聚类覆盖采样，在同等标注预算下的 F1/Recall 提升。

#### 简历需要的数字

- 标注量减少多少；
- 单位 1 万条标注带来的 F1 增益；
- 长尾类别召回提升；
- 争议样本占比及一致性改善。

### P0：补齐 Guard 的评测体系

至少建立五组测试集：

1. **IID 测试集**：与训练数据同分布；
2. **时间外测试集**：按时间切分，检测线上漂移；
3. **来源外测试集**：新业务、新图片风格、新语言；
4. **对抗集**：遮挡、拼贴、低清、旋转、图中文字、隐式表达；
5. **边界集**：争议内容、合理使用、新闻/教育语境等容易误杀的样本。

指标不要只报 F1，还应包括：

- 每类 Precision、Recall、Macro-F1；
- 高风险 Recall 和正常内容误杀率；
- PR-AUC；
- ECE/Brier Score 等校准指标；
- Coverage-Risk 曲线；
- 延迟、吞吐、显存与单次成本；
- 多轮一致性与不同提示改写稳定性。

### P1：使用软标签和争议建模

你的腾讯清晰度项目已经使用分布式软标签，这个思路可以迁移到 Guard：

- 多标注员或多教师模型输出标签分布，而不是强制单标签；
- 将“争议”作为独立状态；
- 用 KL/JSD 学习分布；
- 对高分歧样本设置复核或延迟决策；
- 对严重度使用有序分类或分布回归。

这比简单多数投票更有研究深度，也能直接降低边界样本误杀。

### P1：多教师蒸馏升级为“能力分工 + 校准融合”

可以让不同教师承担不同任务：

- 视觉教师判断图像内容；
- OCR/文本教师判断图片内文字；
- 上下文教师判断多轮对话意图；
- 规则引擎处理确定性高的业务约束。

融合时不要只投票，可学习类别级权重或使用 stacking，并对每个教师做温度缩放/等距回归校准。

### P1：级联推理和风险可控部署

推荐结构：

```text
规则/哈希去重
  → 小模型快速筛查
  → 高置信放行或拦截
  → 中间置信区间进入大 VLM
  → 高影响或多模型冲突样本进入人工
  → 结果回流主动学习池
```

关键不是“用了几个模型”，而是给出：

- 自动处理覆盖率；
- 在指定误杀率下的召回；
- 大模型调用量下降；
- 平均延迟和 P95 延迟；
- 人工审核量下降。

### P2：流式 Guard 与上下文状态

如果业务包含多轮对话，可以增加：

- Token/句子级流式风险头；
- 跨轮风险状态累积；
- 用户输入、模型思考前后和最终输出的三阶段审核；
- 对工具调用参数单独做 Action Guard；
- 风险触发后的安全改写，而不是统一拒答。

### Guard 项目最值得形成的一个研究题目

> **面向长尾风险与动态政策的多模态安全审核：政策条件化建模、争议软标签学习与选择性级联推理。**

如果完成上述 P0，项目会从“做过数据和训练”提升为“有完整研究问题、模型方法、评测体系和部署闭环”。

## 五、渗透测试 Agent 发展到什么程度

> 以下讨论只面向授权靶场、CTF 和企业自有测试环境，不应在未授权目标上运行。

## 5.1 当前成熟度判断

截至 2026 年，渗透测试 Agent 已经从“LLM 提建议”发展到“可在受控环境中调用工具并完成部分端到端任务”，但还没有稳定达到无人值守的真实企业渗透水平。

可以分为四个阶段：

1. **LLM 辅助阶段**：模型负责任务分解和建议，人类执行工具，代表为 PentestGPT。
2. **半自动 Agent 阶段**：模型能规划、扫描、调用工具、读取结果并重试。
3. **多 Agent 闭环阶段**：侦察、搜索、规划、执行、验证由不同 Agent 协作，并有长期状态库。
4. **受监督自治阶段**：在部分 CTF/靶场可以端到端完成任务，但复杂攻击链仍需要 HITL。

公开结果呈现出一致结论：

- Cybench 早期结果中，最佳模型无指导完成率仅 17.5%，说明基础模型长程执行能力有限。
- PentestAgent 在已知漏洞、预构建环境上表现明显提高，但困难任务、复杂 UI、组件识别和攻击链仍是瓶颈。
- CAI 在孤立的 CTF challenge 上很强，但在多阶段 HTB machine 上只在 1/11 场景快于最佳人类；论文也明确认为完全自治仍不成熟。

因此最准确的判断是：

> **当前 Agent 对“边界明确、工具成熟、反馈可验证、已知漏洞为主”的任务已经有实用价值；对开放环境、未知漏洞、长程攻击链、复杂身份系统和高风险决策仍需要专家监督。**

## 5.2 你现有项目的主要不足

旧版描述只有：分层架构、Tool-Calling、RAG、异步并行。缺少以下决定项目含金量的内容：

- 在什么靶场评测；
- 多少目标、多少漏洞类型；
- 端到端成功率和分阶段成功率；
- 平均步骤数、耗时、token 成本；
- 错误恢复成功率；
- RAG、Multi-Agent、并行调度分别带来多少提升；
- 系统如何确认“真的成功”，而不是相信模型自述；
- 如何限制作用域和高风险工具权限。

## 5.3 最值得落地的优化

### P0：用“攻击状态图”代替纯聊天历史

建立结构化状态：

```text
资产 → 服务 → 版本 → 可能漏洞 → 前置条件 → 已执行动作
→ 观察证据 → 当前权限 → 未完成目标 → 失败原因
```

每次行动都必须更新状态图，并区分：

- observation：工具真实输出；
- hypothesis：模型猜测；
- verified fact：经过校验的事实；
- failed attempt：失败动作及原因。

这能显著减少长上下文遗忘、重复扫描和把猜测当事实的问题。

### P0：加入 Planner—Executor—Verifier 闭环

建议不是简单增加 Agent 数量，而是明确职责：

- Planner：生成带前置条件和成功标准的任务 DAG；
- Executor：只执行当前节点允许的工具；
- Verifier：根据工具证据判断是否达成目标；
- Replanner：失败时归因并替换路径；
- Reporter：从证据链生成可复现报告。

每个节点都应包含：输入条件、工具权限、超时、成功判据、失败分类和回滚动作。

### P0：建立真正的 Benchmark

建议优先使用授权环境中的 30～50 个任务，覆盖：

- Web、系统配置、凭据管理、组件漏洞等不同类型；
- 简单单步任务和多阶段机器；
- 已知漏洞与未知组合场景；
- 静态页面和需要浏览器交互的场景。

至少报告：

| 指标 | 含义 |
|---|---|
| End-to-End Success | 是否完成整个目标 |
| Stage Success | 侦察、分析、验证各阶段完成率 |
| Valid Action Rate | 执行动作中语法、参数与上下文正确的比例 |
| Verification Precision | Agent 宣称成功时真实成功的比例 |
| Recovery Rate | 首次失败后通过重规划恢复的比例 |
| Repeated Action Rate | 无效重复动作比例 |
| Steps / Time / Cost | 每个成功任务的步骤、耗时和 token/API 成本 |
| Human Intervention | 每个任务需要人工介入的次数 |

### P1：工具输出结构化与证据绑定

- 将终端原始输出解析为统一 schema；
- 所有结论必须引用证据 ID；
- 对工具参数做类型和范围校验；
- 对成功判定使用确定性检查器，不让 LLM 自己宣布成功；
- 对网页搜索、RAG 文档和代码仓库视为不可信输入，防止提示注入。

### P1：动态模型路由

不同模型适合不同任务：

- 小模型处理日志摘要、参数抽取和重复判断；
- 强推理模型处理规划、失败归因和复杂代码理解；
- 专用模型处理代码漏洞分类；
- 规则模块处理权限、范围和风险控制。

实验中应对比单模型与路由方案的成功率、成本和延迟。

### P1：从静态 RAG 升级为“版本约束知识库”

知识条目至少包含：组件、版本范围、前置条件、适用平台、证据来源、发布时间、可信度和验证状态。检索后再做：

- 多源交叉验证；
- 当前环境版本匹配；
- 依赖和前置条件检查；
- 过期信息过滤。

这比“搜到漏洞文章就交给模型”可靠得多。

### P1：浏览器 Agent 与复杂交互状态

补齐文件上传、登录态、表单、动态页面和多步骤工作流，但要把页面内容视为不可信输入，并隔离页面指令与系统指令。

### P1：安全执行层

这是项目从 Demo 走向工程系统的必要部分：

- 靶场/目标白名单；
- 授权令牌和测试时间窗；
- 容器或虚拟机隔离；
- 网络出口限制；
- 工具分级授权；
- 高风险动作人工审批；
- 资源与次数限制；
- 全链路审计和一键终止。

### P2：训练或优化 Agent 策略

有足够轨迹后再做：

- 从专家轨迹进行 SFT；
- 用成功率、步骤成本、重复动作、非法动作构建过程奖励；
- 对成功/失败轨迹做偏好学习；
- 使用课程学习，从单步任务逐步扩展到多阶段任务；
- 建立“失败类型分类器”，辅助重规划。

不要一开始就强调强化学习，先证明状态表示、验证器和 Benchmark 有效。

## 5.4 最值得做的消融实验

| 版本 | 目的 |
|---|---|
| 单 Agent + 全上下文 | 基线 |
| + 结构化状态图 | 验证长期状态管理 |
| + RAG | 验证外部知识价值 |
| + Verifier | 验证虚假成功率下降 |
| + Replanner | 验证失败恢复能力 |
| + 多 Agent | 验证角色分工是否真的有效 |
| + 模型路由 | 验证成本/效果权衡 |

最终应得到类似结论：在相同测试集上，端到端成功率提升多少，虚假成功率下降多少，平均步骤和成本变化多少。只有这样，“Multi-Agent”才是结果，不是关键词。

## 六、腾讯审单项目可增加哪些 OCR / 文档智能技术

## 6.1 先把项目重新定义

不要把它只定义为 OCR 调参。更好的研究问题是：

> **面向真实法律文书的质量感知文档理解系统：在低清、旋转、多图拼接、印章干扰和长尾版式下，实现可校准、可路由、可回流的结构化识别。**

## 6.2 可落地的整体架构

```text
图像输入
  → 重复/近重复检测
  → 方向、透视、弯曲、光照与压缩失真检测
  → 质量分级与增强策略路由
  → 版面分析与阅读顺序恢复
  → 多尺度 OCR / 标题与字段识别
  → 领域词典与结构约束纠错
  → 置信度校准和一致性检查
  → 高置信自动处理 / VLM 复核 / 人工复核
  → 难例回流与漂移监控
```

## 6.3 P0：建立 OCR 导向的质量标签，而不只是人眼清晰度

当前五级质量可以进一步拆成三个相关但不同的目标：

1. **感知质量**：人眼是否清晰；
2. **OCR 可读性**：文字识别是否可靠；
3. **业务可用性**：关键标题、印章、号码是否足以完成审单。

建议模型多任务预测：

- 五级主观质量分布；
- 预期 CER/WER 或 OCR 失败概率；
- 局部不可辨区域比例；
- 是否需要增强、切图或 VLM 复核；
- 关键字段可用性。

DocIQ 和 DIQA-5000 的思路值得参考：结合低层清晰度、色彩特征和高层文档布局，多头预测质量分布，而非单一分数。

## 6.4 P0：做“增强是否有益”的路由模型

不要对所有图片统一去模糊或超分辨，因为生成式增强可能补出不存在的笔画，反而伤害法律文书可信度。

可构建候选增强池：

- 方向纠正；
- 透视/弯曲矫正；
- 阴影与光照校正；
- 去噪和去压缩伪影；
- 保守型锐化或超分；
- 局部文字区域重采样。

路由模型预测每种增强的 `OCR 增益 - 伪影风险 - 推理成本`，只执行预期收益为正的操作。

### 实验

- 原图 OCR；
- 固定增强后 OCR；
- 质量路由增强后 OCR；
- Oracle 最优增强上界。

指标：CER/WER、关键字段准确率、增强调用率、伪影导致的错误率、延迟。

## 6.5 P0：从整页识别升级为版面感知的级联识别

PaddleOCR 3.0 已把能力拆为 PP-OCRv5、PP-StructureV3 和 PP-ChatOCRv4。你的场景可采用相似分层：

1. 页面方向和文档展开；
2. PP-DocLayout / PP-Structure 做区域与阅读顺序；
3. 标题、正文、印章、表格、号码区域分别识别；
4. 对关键区域使用更高分辨率或更强模型；
5. 对整页结果做结构一致性校验。

这比“整页 OCR 后字符串匹配”更容易处理多图横排、标题错序和复杂版式。

## 6.6 P0：置信度校准与选择性识别

OCR 原始置信度通常不能直接代表正确概率。建议：

- 在独立验证集上做 Temperature Scaling / Isotonic Regression；
- 分文档来源、分辨率、字段类型分别校准；
- 画 Reliability Diagram；
- 设置双阈值：高置信自动处理，中间区间复核，低质量直接退回；
- 报告 Coverage-Error 曲线，而不只报整体 Accuracy。

对于审单业务，这比把整体准确率从 99.9% 写到 99.99% 更可信，因为它直接回答“多少单据可以安全自动化”。

## 6.7 P1：领域约束纠错

可加入三层约束，但要保留原始 OCR 证据：

1. **词汇层**：文书类型、机构名、固定术语、常见混淆字词典；
2. **结构层**：标题位置、案号格式、联系电话格式、印章与落款相对位置；
3. **跨字段层**：正文机构、落款、印章和联系方式的一致性。

可采用候选 lattice + 领域语言模型重排，或者让 VLM 只在候选集合内选择，避免自由生成造成幻觉。

## 6.8 P1：区域级难例挖掘与主动学习

不要只按整页错误回流。建议保存：

- 错误文本框坐标；
- 字符/词级置信度；
- 失真类型；
- 文档来源和模板簇；
- 哪个模块导致错误；
- 人工修正结果。

按“模型分歧 + 低置信 + 新模板 + 高业务影响”采样，形成区域级难例池。这样能明确回答每轮数据迭代解决了什么问题。

## 6.9 P1：教师—学生蒸馏与级联部署

- 大 VLM 作为离线教师，生成版面、文字候选和质量解释；
- 小 OCR/Layout 模型作为在线学生；
- 对争议样本使用 VLM 复核；
- 对固定模板使用轻量专用头；
- 以延迟预算动态路由。

目标指标应同时包括：准确率、自动处理覆盖率、VLM 调用率、P95 延迟和成本。

## 6.10 P1：文档模板与时间漂移监控

真实线上系统会不断出现新机构、新扫描设备和新模板。建议：

- 用视觉/版面 embedding 对文档聚类；
- 监控新簇比例、置信度分布、关键字段缺失率；
- 按时间切分训练/测试数据；
- 新模板触发少样本标注和回归测试；
- 每个模型/规则版本保留可复现评测报告。

## 6.11 腾讯项目需要补的实验矩阵

| 模块 | 基线 | 新方案 | 必报指标 |
|---|---|---|---|
| 清晰度 | XGBoost / 硬标签五分类 | 多尺度文档特征 + 软标签分布 + 多任务头 | Macro-F1、QWK、MAE、SRCC、ECE |
| 图像增强 | 不增强 / 固定增强 | 质量感知动态路由 | CER/WER、关键字段准确率、伪影率、耗时 |
| 文书类型 | 全页 OCR + 模糊匹配 | Layout 标题定位 + 阅读顺序 + 领域约束 | Accuracy、长尾 Recall、模板外准确率 |
| 印章 | 单检测模型 | 多模型融合 + HSV + 选择性分类 | Precision、Recall、自动覆盖率、P95 延迟 |
| 整体链路 | 每模块独立阈值 | 统一置信度校准与风险路由 | 自动通过率、误拦率、漏拦率、人工量下降 |

## 七、应该如何补充两页内容

现在不要立即扩写成两页。先把可验证材料补齐，再决定版面。

## 7.1 第一优先级：补结果，不补形容词

需要向项目记录中补齐：

- 数据集规模、来源、训练/验证/测试划分；
- 正负样本比例和长尾程度；
- 基线模型与旧链路；
- 核心指标及提升；
- 消融实验；
- 线上覆盖率、人工量、延迟和成本；
- 个人负责范围；
- 当前状态：离线、灰度、上线或稳定运行。

## 7.2 第二优先级：补一个外部成果

建议三选一：

1. **文档质量评估 Benchmark/技术报告**：与你腾讯项目最一致，最容易形成算法深度。
2. **安全可控的 Agent Benchmark**：开源评测与状态管理框架，不公开危险利用细节。
3. **多模态 Guard 数据与评测框架**：只开源 Taxonomy、评测脚本和脱敏样例，不泄露公司数据。

## 7.3 第三优先级：再加入旧经历

旧版内容的保留优先级：

1. **企业知识助手**：保留，能补 RAG/Agent 工程能力，且有 300+ 数据源和 150+ 用户量化结果。
2. **自动化渗透测试 Agent**：在完成 Benchmark 和 Verifier 改造后保留；当前版本表述偏泛。
3. **WebAssembly 性能优化**：可作为底层系统能力证明，但与主投方向相关性弱，控制为 1 条。
4. **国家级竞赛和奖学金**：两页版应恢复。
5. **学生工作**：仅保留“纸飞机队长 + 80+ 教师培训”这一条，其他职务可合并或删除。

## 八、建议的 6 周落地计划

### 第 1 周：统一项目记录和指标口径

- 为腾讯、Guard、Agent 各建一张实验表；
- 明确数据切分、基线、指标定义和个人贡献；
- 排查目前简历中 89 万/100 万、99.9%/99.99%、上线状态等口径差异。

### 第 2～3 周：优先补腾讯清晰度项目

- 建立硬标签基线与软标签模型；
- 增加 QWK、MAE、SRCC、ECE 和 OCR 相关性；
- 完成至少 3 项消融：软标签、质量特征、概率期望校准；
- 输出一张完整对比表。

### 第 3～4 周：补 Guard 评测和主动学习

- 建立时间外、来源外、边界和对抗测试集；
- 比较随机采样与分歧/不确定性采样；
- 输出 Coverage-Risk 曲线和类别级 PR；
- 若条件允许，验证政策条件化分类的小规模原型。

### 第 4～5 周：升级 Agent 的可验证性

- 引入结构化状态图、Verifier 和失败重规划；
- 在授权靶场建立 30+ 任务 Benchmark；
- 完成单 Agent、状态图、Verifier、Multi-Agent 的消融；
- 统计端到端成功率、虚假成功率、恢复率、步骤数和成本。

### 第 6 周：形成可验证成果

- 输出一份脱敏技术报告；
- 整理图表和方法架构图；
- 再根据完成结果写两页简历；
- 简历只写实际完成并能在面试中解释的数据。

## 九、项目完成后可达到的表达标准

以下只是结构模板，数字必须来自真实实验，不能直接填入简历：

### Guard

> 面向长尾多模态风险，构建政策条件化审核与主动学习闭环；通过多教师分歧采样和争议软标签降低标注噪声，在时间外测试集上 Macro-F1 提升 X 个百分点；设计小模型—VLM—人工三级选择性推理，在高风险 Recall 不低于 X% 时自动处理覆盖率达到 X%，VLM 调用量下降 X%。

> 在授权靶场构建包含 X 个目标、Y 类任务的评测集，引入攻击状态图、Planner–Executor–Verifier 闭环和失败重规划；相对单 Agent 基线，端到端成功率由 X% 提升至 Y%，虚假成功率下降 Z 个百分点，平均重复动作减少 X%，并通过目标白名单、沙箱和工具分级授权保证执行可控。

### 腾讯审单

## 最终建议

短期最值得投入的顺序是：

1. **先补腾讯清晰度项目的量化结果和消融**，这是最容易形成独特技术标签的项目；
2. **再把 Guard 升级为政策条件化 + 主动学习 + 选择性推理**，体现后训练和评测深度；
3. **最后给渗透测试 Agent 建 Benchmark、状态图和 Verifier**，否则仅靠 Multi-Agent/RAG 关键词不够突出；
4. 完成上述证据后，再制作两页简历，第二页放 Guard 延伸、Agent、WebAssembly、竞赛和社会实践。
