## 2. 介绍京东实习：低代码平台负责什么、有哪些功能、竞品、代码开发及选型

### 2.1 做了什么

在京东 AI 安全团队参与过 Autosec 低代码智能体平台及其应用建设。平台主要把模型、知识库、工作流、Agent、插件和 MCP 工具封装成可编排组件，让业务人员能够较低成本地搭建企业智能体。项目材料能确认我参与的业务包括：主 Agent 意图路由、DeepResearch、新闻检索与推送、RAG、长短期记忆，以及安全工具的 MCP 接入、运行环境封装和平台部署。

一个具体应用是企业新闻助手：主 Agent 负责意图路由、记忆和任务分发；DeepResearch 子 Agent 可以访问 OSS/RAG 数据、在线搜索和交互式爬取；新闻链路负责采集、总结、Elasticsearch 入库、去重、个性化排序和定时推送。

### 2.2 除了低代码，是否写过代码

有。低代码平台适合快速编排，但新闻流水线的数据处理、并发、去重、状态管理和长时间运行使用了代码实现：

- 将 OSS 中包含多条新闻的 JSON 拆成独立任务；
- 使用多线程执行新闻列表获取、下载、总结和上传；
- 建立 Manager 记录成功、模型超时、格式错误等状态，并按错误类型重试；
- 把确定性的重复判断移出大模型节点；
- 使用 TF-IDF 文本相似度和层次聚类合并同一事件；
- 根据地区、相关性、重要性和类型对 ES 召回结果排序；
- 为支持长时任务和并行执行，将部分链路迁移到本地和服务器。

### 2.3 低代码还是代码，怎么选

我主要看五点：

1. **需求阶段**：原型验证、流程频繁变化时优先平台；需求稳定后再沉淀代码服务。
2. **流程复杂度**：简单串并联、标准模型节点和知识库问答适合平台；复杂循环、动态 DAG 和细粒度状态机更适合代码。
3. **性能与规模**：平台存在节点输入、并发和超时限制。项目中 Dify 单次处理数量存在上限，长任务和批量并发最终更适合代码化。
4. **可观测与可靠性**：需要幂等、检查点、精确重试、灰度和完整监控时，代码方案更可控。
5. **安全与复用**：稳定、敏感或高调用量的能力应封装成服务或 MCP 工具，平台只负责编排，不应把密钥和复杂业务逻辑散落在节点中。

实践中不是二选一，而是“平台编排 + 代码服务”：平台负责快速迭代和可视化流程，代码承担复杂、稳定、可复用的能力。

### 2.4 竞品调研怎么回答

现有材料只能证明实际使用过 Dify/内部平台，没有正式、量化的竞品评测记录，因此应如实说没有做过完整竞品 Benchmark。若面试官希望听选型方法，可以从以下维度对比 Dify、Coze、LangGraph 以及云厂商 Agent 平台：

- 工作流表达能力：循环、分支、子图、状态持久化；
- RAG：解析、索引、混合检索、重排和权限隔离；
- 工具生态：插件、MCP、私有 API 和自定义代码；
- 可观测性：Tracing、Token/时延/错误统计和回放；
- 部署与合规：私有化、数据权限、密钥管理；
- 扩展性与成本：并发、长任务、模型接入、二次开发成本。

## 3. 介绍一个有挑战的技术点

**回答：新闻处理流水线的可靠性改造。**

最初新闻采集和总结主要依赖低代码节点，出现了三个问题：一是部分 JSON 内包含多条新闻，任务粒度不统一；二是大模型会返回 `date:<date>` 等格式错误，也会超时；三是重复新闻反复下载和总结，浪费模型调用成本。

我的思路是先重新划分模型和确定性程序的边界。模型只负责新闻摘要、语义相关性和重要性判断；解析、去重、状态判断等确定任务由代码负责。然后将每条新闻拆成独立任务，建立 Manager 记录成功、超时、格式错误和已处理状态，按错误类型做有限次重试；采集与处理阶段并行执行，并使用 URL/处理记录做幂等，推送前再用 TF-IDF 和层次聚类做事件级去重。最后将链路迁移到本地和服务器，以支持长任务和并行。

这个项目让我认识到，Agent 的稳定性不能只靠 Prompt。真正可靠的方案需要明确模型与程序的职责边界，并补齐结构化输出校验、状态机、幂等、重试和可观测性。

## 4. 多模态聊天、意图识别、DeepResearch、RAG、记忆和 MCP

### 4.1 多模态输入聊天怎么做

典型链路如下：

1. 前端将文本和图片作为同一条消息提交，图片先上传对象存储，消息中保存图片引用、类型和必要元数据；
2. 服务端完成格式、大小、权限和安全校验，并按模型要求进行缩放、切片或压缩；
3. 使用模型的 Chat Template 把文本块与图片块组织成统一消息，视觉编码器将图片转换成视觉 Token，再与文本 Token 一起进入语言模型；
4. 会话层只保存图片引用和结构化消息，避免反复传输原图；上下文超长时，对历史进行裁剪或摘要；
5. 输出采用流式返回，并记录模型、Prompt 版本、Token、时延、工具调用和错误信息。

项目材料能确认做过多轮图文安全数据和多模态审核，但没有记录聊天前端上传协议和图片预处理实现。因此上述是标准工程方案，不应说成项目中每一项都亲自落地。

### 4.2 意图识别怎么做

主 Agent 先将用户输入路由到 DeepResearch、查数、写作、提醒或普通问答等子能力。较稳妥的做法是“规则优先 + 模型分类 + 低置信兜底”：

- 明确命令、权限和高风险操作先用规则拦截；
- 让模型按固定 Schema 输出 `intent`、`confidence`、`slots` 和 `reason`；
- 根据对话上下文补齐时间、地区、数据源等槽位；
- 低置信、多个意图冲突或缺关键参数时澄清，不强行路由；
- 离线用混淆矩阵和各意图 F1 评估，线上关注误路由率、澄清率和任务成功率。

### 4.3 DeepResearch 怎么做，子查询怎么获得，是否异步

可以采用 Planner—Worker—Reviewer—Synthesizer 架构：

1. Planner 从原问题中提取目标、时间范围、实体和约束，并生成若干互补子查询；
2. 为子查询建立依赖图，无依赖的检索任务并行，有依赖的任务等待上游结论；
3. Worker 分别调用企业 RAG、在线搜索或网页抓取，保存来源、时间和证据片段；
4. Reviewer 做去重、来源可信度判断和矛盾检测，并根据证据缺口触发补充查询；
5. Synthesizer 只基于保留证据生成结论和引用。

子查询不是简单改写，而应覆盖定义、现状、证据、反例和时间约束；还需做语义去重和查询预算控制。工程上适合使用异步任务队列或协程并发 I/O，但同一域名要限流，任务必须设置超时、重试和取消机制。

**事实边界：**项目材料能确认 DeepResearch 接入 OSS RAG、在线搜索和交互式爬取，也能确认新闻采集使用多线程并行；没有记录 Planner Prompt、动态补充查询和完整异步 DAG，因此这些属于我对标准实现的理解。

### 4.4 RAG 构建工具怎么做

RAG 构建工具可拆成离线索引和在线检索两条链路。

**离线侧：**数据源连接 → 文档解析/OCR → 清洗去重 → 结构化切分 → 元数据与权限绑定 → Embedding → 向量索引与关键词索引 → 增量更新和版本管理。

**在线侧：**问题改写 → 权限过滤 → Dense/关键词 Hybrid Search → 结果融合 → Re-ranker → 上下文拼接 → 带引用生成 → 日志与反馈回流。

项目中实际采用 Hybrid Search 和重排，并使用 Elasticsearch/向量化记忆。关键评测应拆开：检索看 Recall@K、MRR、NDCG 和权限正确率；生成看 Faithfulness、引用准确率、完整性和任务成功率。

### 4.5 长短期记忆怎么做，分别是什么

- **短期记忆**：当前会话最近若干轮消息、工具结果和临时任务状态，用于维持本轮上下文。受上下文窗口限制，需要做窗口裁剪或滚动摘要。
- **长期记忆**：跨会话仍有价值的稳定信息，例如用户偏好、常用地区、角色和历史任务摘要。先抽取候选事实，经过重要性、时效性、权限和冲突检查后写入结构化存储或向量库；新请求到来时按语义、时间和用户隔离条件召回。
- **群组记忆**：团队共享但受权限控制的知识和任务状态，不能与个人私有记忆混用。

长期记忆不是把全部历史聊天永久拼进 Prompt。否则会带来噪声、隐私和过期信息问题。应支持来源、时间戳、置信度、TTL、修改和删除。

### 4.6 MCP 的原理和调用过程

MCP 的核心是用统一协议把模型应用与外部工具、资源和提示模板解耦。MCP Host 承载 Agent，Client 负责连接具体 Server，Server 暴露工具 Schema 或资源。

典型调用过程是：

1. Client 与 Server 建立 stdio 或 HTTP 连接并初始化，协商协议版本和能力；
2. Client 通过 `tools/list` 获取工具名称、描述和参数 JSON Schema；
3. Host 把可用工具描述交给模型；
4. 模型根据用户任务生成结构化工具调用；
5. Client 做权限和参数校验，通过 `tools/call` 请求 Server 执行；
6. Server 在受控环境中运行工具并返回结构化结果；
7. Host 将结果作为 observation 交回模型，模型决定继续调用、重试或生成最终回答。

MCP 解决的是接口标准化和工具发现，不自动解决权限、幂等、超时、审计与安全隔离，这些仍需业务系统实现。

### 4.7 我主要做的 MCP 工具和工作流

项目材料能确认的个人工作边界是：参与安全工具的接入、运行环境封装和平台部署，并在自动化渗透测试工作流中使用端口扫描、目录扫描、指纹识别、漏洞扫描、爬虫和自动化浏览器等能力。不能从现有材料确认本人独立开发的工具清单和数量，因此面试时应补充真实名单，不应把平台已有的 180 个工具说成个人产出。

工作流层面可讲“任务规划—工具选择—沙箱执行—结果标准化—验证—记忆回流”：工具调度器根据目标和已有证据选择工具与参数，执行结果统一转成结构化 JSON，验证模块判断成功、失败、误报或需要人工确认，再将有效轨迹写入记忆。

### 4.8 大模型总结出错怎么办：反思与复盘

先把错误分成检索错误、理解错误、事实冲突、遗漏、格式错误和幻觉，再针对性处理：

1. 每个结论绑定证据片段和来源，没有证据就降低置信度或拒答；
2. 将答案拆成原子事实，逐项做检索回查、规则校验或 NLI 一致性判断；
3. 结构化输出先做 Schema 校验，可修复的格式错误有限次重试；
4. 多来源冲突时同时保留证据和时间，不让模型自行“平均”；
5. 对高风险结论设置人工复核；
6. 记录失败类型、Prompt、检索结果和模型版本，形成 Bad Case 集并回归测试。

项目中的真实经验是：新闻总结出现超时和格式错误后，通过 Manager 分类记录并针对性重试；把去重等确定性任务移出大模型；推送前再使用传统算法去重。复盘结论是：先减少模型不擅长的职责，再谈让模型自我反思。

## 5. RAG 分块时怎么保留文章段落结构

核心原则是先解析结构，再在结构内部控制长度，不能直接按固定 Token 硬切。

1. 解析标题层级、段落、列表、表格、代码块和图片说明，建立文档树；
2. 优先以章节或自然段为边界，小段合并，超长段再按句子或语义边界拆分；
3. 表格、代码块和完整列表尽量作为原子块，不从中间切断；
4. 每个 Chunk 保存文档 ID、标题路径、页码、段落序号及前后关系；
5. 使用 Parent—Child Chunk：较小 Child 用于精准召回，命中后返回更完整的 Parent 段落；
6. 只在同一章节内设置适量 overlap，避免把无关章节粘在一起；
7. 生成上下文时按原文顺序重排相邻块，必要时补充前后段落。

评估不仅看 Recall@K，还应检查“答案所在段是否完整召回”、表格行列是否破坏、标题是否丢失及上下文冗余率。

## 6. 介绍华为校企合作项目

**回答：**

这个项目研究 WebAssembly 运行时性能优化。Wasm 为保证内存和类型安全，需要在运行时执行边界检查等动态检查，但其中一部分检查在编译前可以被证明为冗余。我们的方案是离线、硬件无关并以安全为前提：先由安全分析器在字节码或中间表示上分析哪些检查在所有可达路径上都不会失败；对能证明安全的部分，通过静态重写减少运行时检查；对不能证明的部分仍由原运行时执行，不做激进优化。混合执行器负责兼容优化路径和保守路径。

安全性的核心不是“猜测这次不会越界”，而是保守证明：只有满足安全条件的检查才能移除，分析不确定时必须回退原逻辑。因此优化不会弱化 Wasm 的安全边界。方案不绑定具体 CPU 指令，所以具有硬件无关性。项目材料记录在真实用例和 SPEC CPU Benchmark 上平均获得 12.95% 的性能提升。

**面试前需补齐：**个人具体负责模块、基线运行时、测试硬件、统计方式以及 12.95% 是算术平均还是几何平均；现有文档不足以支持更细的个人贡献描述。

## 7. 自动化渗透测试项目：几个智能体，工具失败怎么办

### 7.1 项目介绍和智能体划分

项目采用“任务规划—策略推理—工具执行”的分层架构，并通过 RAG 注入目标相关知识。设计文档按具体角色列出了 15 个智能体：

- **4 个核心智能体**：任务编排器、记忆管理器、验证专家、工具调度器；
- **7 个领域专家**：侦察专家、漏洞猎手、风险评估器、知识更新器、CTF 解题专家、赏金优化器、利用开发器；
- **4 个学习/进化智能体**：经验学习器、自主学习器、人类教学器、自我进化器。

不是每个任务都启动全部智能体，而是根据企业评估、CTF、安全研究等剧本动态选择。一次常规流程可以概括为：编排器分解任务，侦察专家收集资产，漏洞专家调用扫描工具，验证专家复核结果，记忆模块保存证据和轨迹，最后生成报告。

**口径提醒：**设计文档另有“4+8+4”的文字，与具体角色表和“15 个”不一致。面试时应以实际实现为准；如果部分角色仍处于设计阶段，要明确区分已实现和规划能力。

### 7.2 工具调用失败怎么处理

1. **调用前校验**：检查参数 Schema、目标范围、权限、工具版本和运行环境；高风险动作必须人工审批。
2. **统一结果协议**：将 stdout、stderr、退出码、产物路径和结构化结果统一封装，区分业务无结果与执行异常。
3. **按错误分类处理**：网络抖动、限流和临时超时可指数退避重试；参数错误由模型根据错误信息修正一次；依赖或版本错误切换镜像或备选工具；权限错误不自动重试。
4. **幂等与检查点**：每一步保存输入、状态和产物，失败后从最近检查点继续，避免重跑整个攻击链。
5. **降级与替代**：Nmap 失败可切换其他扫描器，浏览器自动化失败可退回 HTTP 抓取；替代工具结果仍需验证。
6. **验证与人工兜底**：扫描发现必须由验证专家复核；结果不确定或动作风险高时转人工，不能让 Agent 无限尝试。
7. **经验回流**：记录成功率、错误类型、参数和环境，后续用于工具排序和失败预测。

## 10. 双指针：先递增再递减的数组，求不同元素个数

设数组先单调不减、后单调不增。数组左右两端分别是两条单调链的较小端，因此可以像归并两个有序数组一样，从两端向峰值移动。

- 若 `nums[left] < nums[right]`，左端是当前最小值，计数一次并跳过左侧所有相同值；
- 若 `nums[left] > nums[right]`，右端是当前最小值，计数一次并跳过右侧所有相同值；
- 若二者相等，这个值只计一次，并同时跳过两侧相同值。

```python
def count_distinct_bitonic(nums):
    if not nums:
        return 0

    left, right = 0, len(nums) - 1
    count = 0

    while left <= right:
        if nums[left] < nums[right]:
            value = nums[left]
            count += 1
            while left <= right and nums[left] == value:
                left += 1
        elif nums[left] > nums[right]:
            value = nums[right]
            count += 1
            while left <= right and nums[right] == value:
                right -= 1
        else:
            value = nums[left]
            count += 1
            while left <= right and nums[left] == value:
                left += 1
            while left <= right and nums[right] == value:
                right -= 1

    return count
```

**正确性说明：**在任意时刻，尚未处理部分的最小值一定出现在左端或右端，因为左半段从左向峰值非递减，右半段从右向峰值也非递减。每轮取两端较小值并跳过全部同值，不会漏掉更小元素，也不会重复计数；区间最终收缩为空，因此每个不同元素恰好统计一次。

时间复杂度为 $O(n)$，因为每个元素最多被一个指针访问一次；额外空间复杂度为 $O(1)$。
