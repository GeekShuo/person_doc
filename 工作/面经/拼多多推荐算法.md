**一面**

1. 怎么解决LLM幻觉问题
**解答**：大语言模型的幻觉（Hallucination）主要分事实性幻觉和逻辑性幻觉。解决体系涵盖了从训练到推理的全生命周期：
- **训练阶段（治本）**：1. **预训练/SFT数据清洗**：剔除有毒、虚假和自相矛盾的脏语料。2. **引入拒绝回答机制（拒答SFT）**：在指令微调数据中，故意放入模型不可能知道的超出现有知识的问题，并在配对结果中教会它说“我不知道”或“我缺乏相关资料无法回答”，而非胡编乱造。
- **推理阶段（治标快）**：1. **RAG（检索增强生成）**：最立竿见影的工业落地手段，遇事不决先用数据库外挂知识作为上下文作答。2. **系统参数与解码约束**：降低 `Temperature`，采用贪婪解码关闭其发散胡扯的倾向。3. **Self-Reflection（自我反思）**：先让模型生成答案，再另起一个Prompt让模型自己作为判官去核对这段答案的事实矛盾点。

2. DPO 训练的过程是怎么样的，正负概率怎么算
**解答**：
- **DPO（Direct Preference Optimization，直接偏好优化）** 是对强化学习 PPO 的一种程度的简化，去除了麻烦的 Reward Model 且不需要进行回合制探索。它直接在语言模型的策略网络上优化人类的偏好。
- **过程与概率算法**：
  在训练前，准备好一批三元组数据：$(x=\text{Prompt指令}, y_w=\text{人偏好的好回答}, y_l=\text{人不喜欢的差回答})$。
  内存里同时加载两个模型：你要训的策略模型 $\pi_\theta$（能更新梯度），和一个冻结权重的参考模型 $\pi_{ref}$（即SFT完的基础模型）。
  针对同一个 $x$，分别让这俩模型分别去计算生成好回答 $y_w$ 和坏回答 $y_l$ 整句话的累积对数概率。
  接着，利用差值 $\log \pi_\theta(y|x) - \log \pi_{ref}(y|x)$ 来表征模型对于某个回答在训练过程中的“倾向偏离度”。
  最后将正样本和负样本的倾向偏离度相减，再乘上一个缩放系数 $\beta$，送入一个类似Sigmoid的损失函数（如二元交叉熵）中去极小化Loss。直白地说，就是**强迫模型拉大“对好回答产生概率的倍数放大”与“对坏回答产生概率的倍数放大”之间的边距**。

3. MOE架构原理
**解答**：核心是将密集的计算网络（通常是全连接FFN层）切割为若干个小的、参数不共享的专家网络（Experts）。在每次前向传播时，利用一个极小的前置路由网络（Router）对当前输入的Token计算出概率得分，然后采用Top-K（比如16个选2个激活）的方式把特征分派给对应的专门类网络处理最后加权融合。它在不显著拉升单次推理计算量（即推理FLOPs较低）的前提下，硬生生大幅拉升了模型的总参数天花板级别（即容量海量）。

4. RAG如果有噪声怎么办
**解答**：指的是向量检索时把不相关甚至是矛盾的过时文档切片给召回回来了，混入Prompt中误导了LLM。
解决方法：
1. **防患于未然（召回侧优化）**：不要只依赖向量余弦相似度（容易产生形似神不似的泛化噪声），要结合基于关键字的 BM25 稀疏检索组成**双路混合检索（Hybrid Search）**，最后通过 RRF算法倒数排序融合，大幅提高找准率。
2. **中间拦截（引入重排 Re-ranker）**：在文档送给大模型之前，先用一个专门的小模型（如 BGE-Reranker）把召回回来的几十个全片与问题拼接做Cross Attention精准打分交叉对比过滤，截断抛弃低分噪声。
3. **大模型侧（Prompt打补丁）**：在系统模板里严厉加上约束：“你必须**只**依据以下参考资料作答。如果参考资料中没有相关信息或信息有误相互矛盾，请直接回答‘抱歉，资料缺失’，严谨捏造！”

5. 最新强化学习技术了解什么
**解答**：
技术前沿：
- **PPO 变体改进**：包括像PPO-max或者使用RLAIF（用更强大的GPT-4模型代替昂贵的人类去给偏好排序当裁判，进而大大加快流水线）。
- **GRPO算法（基于群体相对的纯Off模型优化）**：DeepSeek大火的技术。
- **强化学习结晶进入长思维链（RL+CoT）**：像OpenAI O1或者最新模型中，抛弃了在人类偏好这种虚无缥缈的东西上做RL，而是彻底转向在“数学/代码”等有绝对可验证对错（Rule-based Reward）的环境里，利用MCTS（蒙特卡洛树搜索）去让模型自我探索尝试复杂的冗长多步思维，做大强化。

6. Deepseek GRPO，讲讲原理和之后的改进
**解答**：
- **原理（Group Relative Policy Optimization，群组相对策略优化）**：它是对PPO的极限瘦身。正常PPO需要一个跟语言模型Actor差不多巨大并吃显存的Critic（价值模型）去计算每个Token的基线来预估Advantage（优势），防止梯度方差过大。GRPO直接把这个占用的显存大头给扔了。它的做法是：对于某个问题指令 $x$，让当前的Actor模型以一定的随机性连续采样生成一组（比如四五篇）不同的文本回答（这就是个Group）。然后用Reward Model或者编译测试器给这组回答分别打个绝对分。接着，把这组分数进行白化/标准化（通常就是组内分数减去均值再除以标准差），算出来的相对Z-Score直接充任所谓的优势函数Baseline。得分在均值以上的变正优势被激励，低于均值的变负惩罚。
- **后续改进**：它可以被无缝切分成多维度的Reward叠加，比如对回答的结果准确性给一个评分计算一个均值差，同时对它输出格式（有没有带有<think>标签）单独给一个规则评分，各种得分按比例合并作为最终指导模型长出各种长板的引导标。

7. 召回索引怎么优化
**解答**：这侧重于RAG向量库在数据量下的工程响应速度与精度：
- **速度优化**：不使用暴力扁平搜索，直接强上 HNSW（层次导航小世界）这类极致基于图的 ANN 近似最近邻强索引，达到对数级超快查询；或采用如 IVF-PQ 等倒排加乘积量化压缩索引来抵消内存天花板限制。
- **质量优化**：在把长文档切块（Chunking）做Embedding前，附加上该文档的全局MetaData（如类别、日期、作者）方便混合结构化过滤；构建父子切片结构（Parent-Child Retriever），即召回时按细致的小块找保证精准度，但喂给模型时把小块所在的更长的大段落全塞过去，保证上下文不断崖。

8. 意图识别LLM输出格式不好怎么优化
**解答**：
这是做Agent智能体常见的通病：模型废话连篇、输出不闭环JSON。
- **软硬兼施法**：
  1. **Prompt强压**：加入“如果你输出多余废话导致解析失败，你将被惩罚，只能输出由{}包裹的JSON”。
  2. **Few-Shot打样**：在Prompt里手把手给两个标准的意图和它对应的规范JSON样例作为对话历史让它抄作业。
  3. **后端代码兜底拦截（正则+循环提示）**：写死Python代码如果JSON序列化失败，截取带有错误的原文让LLM重新发反思自我修复（Self-Correction）。
  4. **终极必杀：强制约束解码（Constrained Decoding）**：从最底层的推理引掣（如开源的vLLM、SGLang、或者Guidance库）端入手，在生成下一个Token时，代码在底层过滤掉所有不符合提前定义好的JSON Schema语法树的字符概率。模型就算想乱说废话，它的拼音也蹦不出来。

**二面**

1. RAG常用的检索方式
**解答**：
- **单纯的密集检索（Dense Retrieval）**：一切万物全转成Embedding向量，然后算余弦相似度。对语义概括找相似非常有用，但一旦遇到类似找“X-19E42T产品说明”这种特殊长偏怪型号就直接拉胯找不到。
- **单纯的稀疏检索（Sparse Retrieval）**：传统搜索引擎的看家本领，如 Elasticsearch 中的 BM25。纯靠看交集字面词频和逆文档频率计算。专抓专业长尾怪词，但对人类那种拐弯抹角隐晦提问的语义（如“苹果”到底是吃的水果还是手机公司）理解不能。
- **目前的标配（混合检索 Hybrid Retrieval）**：双管齐下全拿来，各自查出来的几十篇文档做 RRF（Reciprocal Rank Fusion 倒数排序融合打分合并），最后经过一把统一重排取前三。效果绝对最稳。

4. RAG遇到模型缺失电商知识一般怎么做
**解答**：
RAG虽然能喂外部知识，但是当由于大模型Base在出厂预训练时**完全没见识过**你们电商赛道的特有语料（专业黑话、特定的运营口吻），只靠RAG塞到上下文里它由于底蕴太浅容易产生极强的阅读理解偏差（抓不住电商核心重点）。
**唯一解法**：拿大量你们电商内部过去的脱敏长对话数据，甚至是各种商品标准参数大拿文章，去对基座模型进行一番**全参/LoRA垂直领域指令微调（SFT）**或者**领域持续预训练（Continual Pretraining）**。先把它训练得像一个老电商懂行人（内化出电商“常识”权重），再配上RAG去外挂实时商品的库存底单文档，就是无敌组合了。

5. Qwen3的技术原理
**解答**：*(注：目前开源为Qwen2.5系列和深度的QwQ体系)* 核心在于：极尽全力打造业界最强的数据清洗构建飞轮，引入合成数据爆发式增加预训练包含代码、多语言、长周期数理符号在内的超高质量密度（几万亿级别高质量Tokens）。并通过长链条RL和拒绝采样强化代码生成质量。架构上继续沿用极致打磨的GQA以保证推理又快又轻。

6. 怎么防止客服LLM串台问题
**解答**：
“串台”通常意味着会话底座被不同用户的输入搞混脏了数据池，或者模型忘却了自己预设的服务某类人的特殊身份立场。
1. **严格在系统后端工程上隔离 Session ID**，每一个进来的不同客户必须实例化一套干净独立的上下文队列对象（History Messages List），严禁任何多线程变量交又读写。
2. **在 System Prompt 层级严防死守**。每一轮新带上的历史对话上方，都铁打不动地置顶强调：“你是且仅是负责接待当前这唯一一位正在提问的用户的官方客户”。
3. **及时修剪截断无用历史记忆**。如果是很长的多轮来回，早期讨论别的话题要及时舍得从List里扔出去或者做向量化压缩，防止废话占用主Prompt注意力焦距偏移导致人设和逻辑混乱失效。

🌟代码：字符串解码
**解答**：LeetCode 394 题，如输入 `"3[a2[c]]"`。
**核心思路：用辅助栈（Stack）**
```python
def decodeString(s: str) -> str:
    stack = []
    res = ""
    multi = 0
    for c in s:
        if c == '[':
            # 入栈保存外层的前缀结果和当前数字倍数，准备在括号内清空后重算
            stack.append((multi, res))
            res = "", multi = 0
        elif c == ']':
            # 当前内层字母记录结束，出栈找寻主人倍数和老前缀进行拼装嫁接
            cur_multi, last_res = stack.pop()
            res = last_res + cur_multi * res
        elif '0' <= c <= '9':
            # 注意有多位数字如 '100'
            multi = multi * 10 + int(c)
        else:
            # 正常字母直接拼于当前层结果
            res += c
    return res
```
